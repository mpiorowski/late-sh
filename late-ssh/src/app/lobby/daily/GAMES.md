# Daily games: the roster's rules

Each correspondence game's rules and the files that implement them. Part of the daily games domain (`CONTEXT.md`: the service, persistence, invariants; `UI.md`: the surfaces); pool is `POOL.md`.

## Adding a game to the roster

`games.rs` is deliberately one enum, no trait objects. Add a variant to `DailyGame` and the compiler walks you through every exhaustive match: DB kind string (`DailyMatch::GAME_KIND_*`), lowercase command `label`, title-cased `display_name` (the #lounge result line uses it), win payout, reward key, ledger reason, tagline. A game with per-player hidden state (like battleship's fleets or the card games' hands) also owes a hidden view in its board renderer for both the opponent and spectators (see `battleship_ui::spectate_waters_lines`, `briscola_ui`). Beyond the enum you owe: a state module (serde state + pure rules, like `battleship.rs` / `connect4.rs`), a `claim_challenge` initial-state arm and a `play_move` dispatch arm in `svc.rs`, a `DailyGameDetail` variant + board input ops in `state.rs`, a board renderer (like `battleship_ui.rs` / `connect4_ui.rs`), a `live.rs::MatchSummary::of` arm (move count plus the live board: reuse a `LiveBoard` shape, as chess960 and the pool games do, or add one, which the compiler then walks through `live_board.rs::board_lines` and `live_strip.rs`'s standing and last-event text), and a migration seeding `daily_<game>_win_payout` in `reward_templates` (plus the key const in `late-core/src/models/reward.rs`). The displayed prize (`DailyGame::win_payout`) and the seeded template's `reward_chips` must stay in sync: the template is what actually pays.

A **variant** of a game already on the roster is much cheaper: chess960 is a second `DailyGame` arm over the same state type, detail struct, rules and renderer, so it owes only the enum arms, a claim arm choosing its opening position, a `DailyGameDetail` variant holding the same detail struct (so `kind()` stays honest), and its reward-template migration. Reach for that only when the two games really are one game with different setup; anything with its own rules gets its own module.

A new way for a match to end is a `DailyResult` variant (`late-core/src/models/daily_match.rs`): the compiler walks it through `as_str`, `state.rs::result_phrase`, `board_ui.rs::result_banner` and `live.rs::finish_headline`. No match over a roster enum (`DailyGame`, `DailyGameDetail`, `LiveBoard`, `DailyResult`, `MatchStanding`, `DailyEvent`) has a wildcard arm; keep it that way, so a new variant breaks the build everywhere it owes an answer.

The compiler cannot demand everything. Grep-hunt these seams too: `DailyResult::ALL` (a variant missing from it compiles, then every row carrying it is left out of the snapshot as `unknown_result`), the challenge copy in `app/help_modal/data.rs` (static strings enumerate the roster), and this file.

**Move channel.** Most games' move is a single cell/column: `play_move(from, to)` carries it (chess uses both, battleship/connect4/reversi pack it into `to`), and `board_select_or_move` dispatches per `DailyGame`. Checkers, backgammon, cribbage, and gin rummy are the exceptions. Checkers' and backgammon's moves are variable-length sequences, and a cribbage discard is two cards while a gin move is a draw or a discard that may knock, so each rides its own typed channel end to end (`play_cribbage_move_task` with a `CribbageMove`, `play_gin_move_task` with a `GinMove`; `play_move` bails for all four): `svc::play_checkers_move_task(user_id, match_id, path: Vec<usize>)` → `play_checkers_move` (shares `move_prelude` with `play_move`, which now only turn/deadline-guards) → `play_checkers`, and `svc::play_backgammon_move_task(user_id, match_id, hops: Vec<backgammon::Hop>)` → `play_backgammon_move` → `play_backgammon`; the client builds the checkers path in `CheckersDetail.pending` (`state.rs::checkers_select`, prefix-matching legal moves so multi-jumps chain click-by-click) and the backgammon turn in `BackgammonDetail.pending` + `selected` (`state.rs::backgammon_select`, lift a checker then land it, hop by hop against the legal-turn prefixes), with Esc clearing either via `cancel_pending_move`. Reversi and checkers are cell-cursor games (row 0 drawn at the top like battleship, `target_geometry` maps a click to a cell); the `board_move_cursor` and `board_input` mouse arms handle both 8x8 boards together. Backgammon's cursor instead walks a visual 2x14 slot grid (six points, the bar, six points, the off tray, twice) that `backgammon::slot_target` resolves to a point/bar/off from the viewer's seat; its mouse arm divides `target_geometry` into the same slots.

## Rules

- **Chess960 rules:** ordinary chess from a shuffled back rank. One of the 960 legal openings is rolled at claim time (`chess_core::rules::random_chess960_board`: bishops on opposite colours, king between its rooks, Black mirroring White) and lives on in the stored FEN; nothing after move zero differs from chess, so the state type, rules kernel, board renderer, results, and 500-chip payout are all the chess ones. The one thing a player notices: **you castle by moving your king onto your own rook**. The lichess-style two-square push is only offered when the king happens to start on e1/e8, because from anywhere else that same pair is an ordinary king step (see `app/games/chess_core/CONTEXT.md`).
- **Battleship rules (v1):** both fleets (5/4/3/3/2) are placed randomly at claim time (a placement phase would cost a whole correspondence day); the coin flip picks the first shooter, one shot per turn on a 10x10 grid, a hit fires again (deadline still resets), sinking all five ships finishes with result `fleet_sunk`.
- **Connect four rules:** 7x6 grid, the claim-time coin flip picks who's red (red drops first), one drop per turn, the turn always passes. Four in a row finishes with result `four_in_a_row`; 42 drops with no line is a `draw`. The state stores only the drop history: grid, turn, and move count are derived, so the state can't self-contradict.
- **Reversi rules:** 8x8 Othello, the claim-time coin flip picks who's black (black moves first), one disc per turn, a legal move must flip at least one bracketed opponent disc. A player with no legal move is auto-passed (passes are NOT stored: `turn()` resolves them by replay, so `next_turn` can come back to the mover). Neither side able to move finishes it: most discs wins (`most_discs`), an equal split is a `draw`. State stores only the placement history from the fixed four-disc opening; board/turn/counts are derived.
- **Checkers rules:** 8x8 American draughts on the dark squares, the claim-time coin flip picks who's red (red moves first, up the board). Captures are mandatory (a jump chain is played to completion: a partial chain never matches a legal move), a man crowned on the far rank ends the turn at once, and reaching the back rank makes a king. Blocking or capturing every enemy piece finishes it (`no_moves`); the forty-move rule (no capture, no man move) is a `draw`. State stores only the move history (each turn a path of squares); there are no passes: a side with no move simply loses.
- **Briscola rules (the roster's first hidden-hand game):** two players, 40 cards (a standard deck minus the 8s/9s/10s), three each, the next card turned up as the trump and left under the stock so it is the last card drawn. The claim-time coin flip picks seat 0, who leads the first trick. There is no obligation to follow suit: the leader plays anything, the follower answers with anything, and the trick goes to the highest trump, else the highest card of the led suit (A > 3 > K > Q > J > 7 > 6 > 5 > 4 > 2). The winner draws first, then the loser, then leads. 120 points are on the table (A 11, 3 10, K 4, Q 3, J 2) and passing 60 settles it, so `apply_play` finishes the match the moment either side is past 60 (`most_points`); 60-60 after all twenty tricks is a `draw`. The state is the connect-four pattern taken further: `{deck, plays}` and nothing else. The deal is the match's entire supply of randomness (contrast backgammon's per-turn server rolls), so every draw is a replay of a fixed order and `table()` derives hands, turn, scores, and trick history from the history alone. **Hidden information is a rendering rule, not a data one:** the state holds both hands and the stock, exactly like battleship holds both fleets, and `briscola_ui` is the only thing standing between them and the screen. It draws faces for the viewer's own hand only, backs for the opponent's, and no faces at all for a spectator. That is safe because the TUI renders server-side over SSH; there is no client to leak to. Both captured-point totals are shown throughout, a deliberate deviation from the table game, where counting only your own pile is part of the skill: across a move-a-day match that stops being memory and becomes note-taking.
- **Cribbage rules:** the six-card two-player game to 61, the short game (once around the board): the full game's 121 runs to months at a move a day. `WINNING_SCORE` is the one dial. The claim-time coin flip picks seat 0, who deals the first hand; the deal alternates. Pone discards two to the crib, then the dealer (one move each, a `CribbageMove::Discard` of both cards), then the starter is cut (a jack pegs the dealer two). Pegging runs to 31: fifteen and 31 peg two, pairs 2/6/12, runs their length; a player who cannot play says go automatically, and the last card of a count pegs one unless it made 31. Then the show, counted by the rules in order (pone's hand, the dealer's, the crib, each with the starter: fifteens, pairs, runs, flush, nobs; a four-card flush counts in hand but not in the crib). First to 61 wins on the spot, mid-pegging or mid-show (`pegged_out`); there is no draw. **The state is `{seats, deals, moves}`**: hands, the crib, the count, the turn and the score are all derived by replay, and each hand is its own shuffle appended by the service when a hand is counted out (`deal_next`, backgammon's durable server randomness), so an optimistic client never deals: its last card leaves the board on `Dealing the next hand…` until the reload. `parse` replays the whole history once and refuses one that does not replay or holds a deal nobody reached, which is what lets `table()` trust it afterwards. Hidden information is briscola's rendering rule: the state holds both hands, the crib, and the uncut starter, and `cribbage_ui` draws faces for the viewer's own hand only; the crib stays face down until the show, whose breakdown the rail keeps through the next hand. A discard is picked on the board (Space marks up to two, Space on a marked card sends both, Esc puts them back); the discard's move-feed label never names its cards. The player bars double as the peg board.
- **Gin rummy rules:** ten cards each, first to 100 across hands. Seat 0 (the coin flip) deals first; the deal alternates, and the non-dealer plays first straight into an ordinary turn (the table game's offer of the first upcard is left out). **A turn is two moves, a draw then a discard**, because the draw must be committed before the drawn card is seen; the service keeps the turn's clock across the draw (`update_state` with the row's own deadline), so a turn is still one day. A stock draw is the one move the board never applies optimistically: it is sent with `move_in_flight` set and the card first appears when the committed row reloads (`gin_drawn_cursor` lands the cursor on it), so a failed write cannot leak the top of the stock; a draw from the pile is public and stays optimistic. The card just taken from the pile cannot go straight back: the board dims it, never picks it, and the status line says why. A discard may knock with 10 or less deadwood; none is gin. Melds and layoffs are never declared: `best_melding` finds the least-deadwood arrangement (sets and runs may share a card, so every combination of candidate melds is searched), and the defender's answer to a knock tries every arrangement with the most layoffs it allows. Knock scores the deadwood difference, a defender at or under the knocker undercuts for the difference plus 25, gin scores 25 plus the defender's deadwood with no layoffs; the hand is dead with two cards left in the stock. First to 100 wins (`reached_hundred`); the table game's line and box bonuses are left out, since the chip prize is fixed, and there is no draw. Same `{seats, deals, moves}` state and server-side `deal_next` as cribbage. The hand is drawn melds first (`Table::held`, the order the cursor walks too) with the melds and deadwood spelled out under it, and the status line previews the deadwood a throw leaves; Space picks a card and Space again throws it, `g` knocks with the picked card. The discard pile is public, drawn fanned on the table and kept whole in the rail; a stock draw is never named anywhere but the drawer's own hand.
- **Backgammon rules:** standard board, no doubling cube (the payout is the fixed reward template), the claim-time coin flip picks who's white (white plays first with a server-rolled non-double opening). One turn per day: the stored `next_roll` is played as hops (doubles = four), bar checkers enter first, maximal dice must be used (higher die when only one plays), lone checkers are hit to the bar, bearing off needs the whole side home. First to bear off all fifteen wins (`borne_off`). The state is `turns: [{roll, hops}]`: dice are durable server rolls stored per turn, forced passes are recorded as turns with no hops (so turn = parity), and `roll_next` (server-only) rolls for the next mover after each move, auto-recording passes until someone can play; a defensive stall cap (100 straight passes) draws a theoretically-wedged match. Clients applying a turn optimistically never roll: `next_roll` stays empty until the reload lands.

## Files

| File | Responsibility |
|---|---|
| `battleship.rs` | Battleship rules, pure logic: `DailyBattleshipState` (the persisted `state` JSON for battleship matches), random legal fleet placement, `apply_shot` (bounds/repeat validation, sunk + fleet-sunk outcomes), `cell_label` (`A1`..`J10`). |
| `connect4.rs` | Connect four rules, pure logic: `DailyConnect4State` (persisted `state` JSON: red/yellow ids + drop history; grid/turn/count all derived), `apply_drop` (bounds/full-column validation, win + draw outcomes), `winning_line` for the end-of-match highlight, `column_label` (`a`..`g`). |
| `reversi.rs` | Reversi rules, pure logic: `DailyReversiState` (persisted `state` JSON: black/white ids + placement history from the fixed opening; board/turn/counts derived, forced passes resolved by replay in `turn()`/`replay()`), `apply_move` (bracket-flip validation, most-discs/draw outcomes), `legal_moves`/`preview_flips` for the UI hints + ghost, `disc_counts`, `cell_label` (`a1`..`h8`). |
| `reversi_ui.rs` | Reversi board renderer: one 8x8 grid (row 0 at top), legal squares hinted, ghost disc under the cursor, per-side disc counts; black `●` / white `○`. Same pinned-hints/centred-stack shape as the others; `target_geometry` maps a click to a cell. |
| `checkers.rs` | Checkers rules, pure logic: `DailyCheckersState` (persisted `state` JSON: red/white ids + move-path history; board/turn/draw-clock derived), `legal_moves` (mandatory-capture + full-chain jump enumeration via `capture_paths`), `apply_move(path)`, `status`/`piece_counts`, `Piece`/`Color`, `cell_label`. `SIZE` (8) is the shared board-size const the wiring references for both cell-cursor games. |
| `checkers_ui.rs` | Checkers board renderer: one 8x8 grid on the dark squares, the in-progress `pending` path lit and legal next squares hinted so multi-jumps build click-by-click, per-side piece counts; men `●` / kings `◉`, red warm / white bright. |
| `backgammon.rs` | Backgammon rules, pure logic: `DailyBackgammonState` (persisted `state` JSON: white/red ids + `turns` of `{roll, hops}` + pending `next_roll`; board/turn/pips derived by replay), `legal_turns` (maximal-dice enumeration over both die orders, bar entry, hits, bear-off wastage, higher-die rule), `apply_turn`/`roll_next`/`preview`, `status` (win by bear-off, stall-cap draw), `point_name` notation, and the 2x14 cursor-slot mapping (`slot_target`, `BgTarget`) the renderer and input share. |
| `backgammon_ui.rs` | Backgammon board renderer: two rows of six point columns around the bar, off tray at the right edge, checker stacks growing toward the middle (overflow collapses into a count), the pending roll as numbered dice tiles between the halves (die-face glyphs are unreadable at terminal sizes), a short how-to in the info rail, lifted-checker landing hints, pending hops previewed via `state.preview`; player bars carry off counts and pips. |
| `briscola.rs` | Briscola rules, pure logic: `DailyBriscolaState` (persisted `state` JSON: seat ids + the 40-card deal + the play history, nothing else: hands, turn, scores, and trick history are all derived by `table()`), `Card`/`Rank` (briscola's own rank order and card points; serialized as a `u8` id, so an out-of-range card cannot be deserialized and the rules never re-check for one), `apply_play` (hand-membership validation, trick + finish outcomes), `settle` (past 60 wins, an even split at the last trick draws), `draw_at` (the stock, then the turned-up trump last). Faces are drawn through the shared `app/games/cards.rs` renderer. |
| `std_deck.rs` | The standard 52-card deck cribbage and gin rummy share: `Card`/`Rank` (ace low, `value()` with face cards at ten, serialized as a `u8` id so an out-of-range card cannot be deserialized), `shuffled_deck`, `is_whole_deck` (the boundary check both states' `parse` run on every deal), `sort_by_rank`. |
| `cribbage.rs` | Cribbage rules, pure logic: `DailyCribbageState` (persisted `state` JSON: seat ids, one deal per hand, the move history; everything else derived by `table()`), `CribbageMove` (`Discard([Card; 2])` / `Play(Card)`), `Phase`, `apply_move` (phase, holding and 31 validation; go and last card resolved automatically in `advance`), the show (`count_hand`, `Count`, `Show`), `deal_next` (server-only), `MoveOutcome::label` for the move feed. |
| `cribbage_ui.rs` | Cribbage board renderer and the one place its hidden information is enforced: your hand fanned face up (unplayable cards dimmed while pegging, marked crib picks lit), the opponent's as backs, the starter, the crib as a back and the cards on the current count in the middle, peg-track player bars, and a rail with this hand's pegging and the last show's breakdown. Records the hand as `card_slots`. |
| `gin.rs` | Gin rummy rules, pure logic: `DailyGinState` (the same `{seats, deals, moves}` shape as cribbage), `GinMove` (`Draw(Pile)` / `Discard { card, knock }`), `Phase`, `apply_move` (draw, throw-back and knock validation; knock, gin, undercut and dead-hand settlement), `best_melding` / `deadwood_after_discard` (exhaustive meld search over candidate sets and runs), the defender's layoffs, `deal_next` (server-only). |
| `gin_ui.rs` | Gin rummy board renderer and the one place its hidden information is enforced: your hand fanned melds first, the opponent's as backs, the stock and the newest discards, a meld/deadwood line, a status line previewing the deadwood a throw leaves, and a rail with every hand's result, the last hand laid down, and the whole discard pile. Records the two piles (while drawing) or the hand (while discarding) as `card_slots`. |
| `hand_ui.rs` | The card rows cribbage and gin share: fanned hands over the `cards.rs` themes (`Tier::Full` five-line, `Tier::Compact` one-line), `CardSlots` (the render-recorded row a click maps back through, read by `board_input`), suit colours, cursor marker. |
| `briscola_ui.rs` | Briscola board renderer, and the one place hidden information is enforced: your hand face up along the bottom, the opponent's as backs along the top, the trump and the open trick (or the trick just taken) in the middle, both scores on the player bars, trick history in the rail. A spectator gets backs on both sides. Two size tiers straight from the shared card themes: `Outline` five-line cards, `Boxed` one-line cards when the board shares the screen with chat. `target_geometry` covers the three fixed hand slots, so a click maps to a card however few are left. |
| `battleship_ui.rs` | Battleship board renderer: "their waters" target grid (cursor, shots, end-of-match ship reveal) beside "your fleet", per-side afloat counts, salvo-history rail, same pinned-hints/centred-stack shape as chess. |
| `connect4_ui.rs` | Connect four board renderer: one gravity grid, `▼` drop indicator + ghost landing disc in the cursor column, last-drop highlight, winning line as solid tiles on finish, drop-history rail, same pinned-hints/centred-stack shape. |
