# Daily Games Context

## Metadata
- Scope: `late-ssh/src/app/lobby/daily` (correspondence-game service, game roster, sidebar panel, full-screen boards) plus its persistence in `late-core/src/models/daily_match.rs` and migrations `102_create_daily_matches.sql` / `105_seed_daily_battleship_reward.sql` / `106_seed_daily_connect4_reward.sql` (reversi/checkers/backgammon/briscola/chess960 seeds: 115/116/117/128/142; eight-ball/nine-ball/snooker: 176/177/178; cribbage and gin rummy: 213).

- Status: Active

- Companion docs: `GAMES.md` (per-game rules, files, adding a game), `POOL.md` (eight-ball, nine-ball, snooker), `UI.md` (panel, strip, modal, board screen).

## 0. Context Maintenance Protocol [STABLE]

Read this after root `CONTEXT.md` whenever a task touches daily matches, challenges, the game roster, the Daily Games sidebar panel/modal/boards, or the `daily_matches` table.

- Update this file when the match lifecycle, deadline policy, cap, payouts, the game roster, or UI surfaces change.
- Update root `CONTEXT.md` when global keybindings, the screen list, or the data model change.
- Chess rules/rendering primitives are NOT owned here: they live in `app/games/chess_core` (see `app/games/chess_core/CONTEXT.md`). Battleship, connect four, reversi, checkers, backgammon, briscola, cribbage, and gin rummy rules ARE owned here (`battleship.rs`, `connect4.rs`, `reversi.rs`, `checkers.rs`, `backgammon.rs`, `briscola.rs`, `cribbage.rs`, `gin.rs`): no other surface plays them. Pool is the other exception alongside chess: its physics, rulesets and renderers live in `app/games/pool_core`, and `pool.rs` here is only the match wrapper. Briscola draws its cards with the shared `app/games/cards.rs` renderer but owns its own rank set, since briscola's rank order and card points generalize to no other game. Cribbage and gin rummy share the standard 52-card deck in `std_deck.rs` (ace low, face cards count ten, the same for both) and the fanned card rows in `hand_ui.rs`.
- `mod.rs` stays declaration-only.
- Adding a game (or a variant, or a new `DailyResult`) to the roster: `GAMES.md`, Adding a game to the roster. The compiler walks most seams; that section lists the ones it cannot.

## 1. Summary [STABLE]

A daily match is a relationship between two people, not a place: no seats, no ready-up, no AFK timers, no live actor per match. What is shared with table chess is the chess itself, through `app/games/chess_core`; every other roster game's rules live entirely in this domain.

Match chat + voice: a claimed match DOES get a chat room. It is a `chat_rooms(kind='game', visibility='public', auto_join=false)` row (slug `daily-{match_id}`, `game_kind` = the roster kind string) plus an enabled `voice_channels(target_kind='chat_room')` (display name `{game label}: {challenger} v {opponent}`), all created inside the claim transaction with both players' memberships (`ChatRoom::create_daily_match_room`); `daily_matches.chat_room_id` (migration 109, `ON DELETE SET NULL`) links them. `kind='game'` buys the existing hidden-from-rail / no-Mentions / no-IRC behavior; `visibility='public'` lets a spectator join from the board and talk (and, since membership is the voice ticket too, sit in the match's voice channel). Matches claimed while match chat was players-only kept a `private` room: `ChatService::join_game_room` answers `GameRoomJoin::PlayersOnly` for those, the spectator never becomes a member, and their board draws no pane. Chat attaches to the match, not the game, so new roster games inherit it with zero per-game code. Open challenges have no chat (nobody to talk to); matches claimed before migration 109 have `chat_room_id = NULL` and render without the pane. Chat rooms + voice channels are reaped by the sweeper once a match has been finished/cancelled 30+ days (`DailyMatch::delete_stale_chat_rooms`, hourly cadence on the 60s loop), aligned with the unseen-result window. There is deliberately no unread-chat signal in v1: the your-turn glow is the nudge, and opening the board marks the room read.

Core shape:
- **A roster of games, one enum.** `games.rs::DailyGame` (chess, chess960, battleship, connect four, reversi, checkers, backgammon, briscola, cribbage, gin rummy, eight-ball, nine-ball, snooker) owns every per-game fact: `daily_matches.game_kind` string, label, win payout, reward key, ledger reason. Challenge posting picks a game (the Lobby's `c`/`C` draft picker); everything downstream dispatches on it. See §0 for the add-a-game checklist.
- **Open lobby is the centerpiece.** Anyone posts an open challenge; anyone claims it; claiming starts a match. Open challenges persist until claimed or cancelled (no expiry in v1). There are no directed challenges: every challenge is open to the whole lobby.
- **24h per move, fixed in v1.** Missing the deadline forfeits (sweeper, §3).
- **Cap: 10 active entries per user** (`DAILY_MAX_ACTIVE_ENTRIES`): open challenges you posted plus active matches you play in, combined. This exceeds the panel's 4 match slots on purpose: the sidebar is a top-4 view of the most actionable matches (your-turn first, nearest deadline within), and the full set is always visible in the Lobby modal.
- **Winner payout** through the existing reward-template path, one `per_event` template per game: `daily_chess_win_payout` 500 chips (migration 102), `daily_chess960_win_payout` 500 chips (migration 142), `daily_battleship_win_payout` 300 chips (migration 105), `daily_connect4_win_payout` 400 chips (migration 106), `daily_reversi_win_payout` 400 chips (migration 115), `daily_checkers_win_payout` 400 chips (migration 116), `daily_backgammon_win_payout` 400 chips (migration 117), `daily_briscola_win_payout` 400 chips (migration 128), `daily_cribbage_win_payout` / `daily_gin_win_payout` 500 chips each (migration 213, both played over several hands), `daily_eightball_win_payout` / `daily_nineball_win_payout` 400 chips each (migrations 176/177), `daily_snooker_win_payout` 700 chips (migration 178, dearer because a frame is the longest match on the roster by a distance). Prizes are shown on lobby rows and in the challenge draft; `DailyGame::win_payout` is the displayed number and must match the seeded `reward_chips`. **Two gates on the payout:** a win pays only if at least `DAILY_WIN_MIN_MOVES` (5) half-moves were played (a resign is not a move; a timeout counts the moves that were made), and at most one win per opponent per game per UTC day the match was **posted** (not finished) is paid: the `pair_day` claim carries the template's `game` like every claim row, so chess and battleship against the same person on the same day both pay. Keying on the posting day is what keeps honest play whole: two long games against the same person posted on different days both pay whichever day they end. A refused win finishes the match normally, posts the #lounge line, tells a connected winner in the banner why no chips came, and stores the reason in `daily_matches.win_payout` for the lingering result row (`you won · resign · no chips, under 5 moves`).
- **#lounge result line (the one activity daily games publish).** When a match *finishes*, and only then, never on posting or claiming, `finish_events` fires one `ActivityPublisher::daily_result_task`, and emits a single `ActivityKind::DailyResult { game }` event: `won a game of {Game}` for a decisive result (attributed to the winner, naming only them: the loser is never resolved, so the feed never shames whoever lost) or `drew with {other} at {Game}` for a draw (a draw shames no one, so both players are named). `filter::lounge_includes` approves it, so it posts to #lounge as a system line (one per match). The game name is `DailyGame::display_name()` (title-cased: "Chess"/"Battleship"/"Connect Four"), a required exhaustive method distinct from the lowercase command `label`. Chips remain the only *economy* footprint (no quest integration); `DailyService` holds an `ActivityPublisher` solely for this line.
- **Per-game rules** (chess960, battleship, connect four, reversi, checkers, briscola, cribbage, gin rummy, backgammon) are in `GAMES.md`; pool is `POOL.md`.
- **Pool (eight-ball, nine-ball and snooker):** the roster's only simulated games, and the one place the "a variant is one game with different setup" rule bends. The rules, the aim, the replay and the board are in `POOL.md`.
- Four UI surfaces, one system of record: the passive right-sidebar Lobby panel, the #lounge live strip (`../../live/CONTEXT.md`; a match in progress painted small at the top of the Home chat card, up only while something just happened), the Lobby modal (`Ctrl+G`, all interaction; "Lobby" is the user-facing name for the whole daily surface), and the full-screen board (`Screen::DailyMatch`, entered from the modal or a click on the strip; renders the match's game).

Unseen results: a finished match stays visible to each player until that player has seen the result, because a correspondence loss (especially a timeout) usually lands while its loser is offline. Acknowledgment is per-player and durable (`challenger_result_seen_at`/`opponent_result_seen_at` columns, migration 108): opening the board and leaving it acks, `x` on the modal row acks without opening, merely opening the modal does NOT (results are news, not liquidity: skimming past must not clear them). Unseen results never count against the entry cap (`count_active_entries` only counts open + active) and surface in three places: result rows at the top of the modal's "your matches" section, panel slots (`you won` / `you lost` / `draw`), and the sidebar `lobby` rule glow. The snapshot's `finished_matches` list is bounded by a 30-day window so a player who never returns can't pin rows forever; migration 108 backfills both seen columns on pre-feature finished rows so old results don't resurface on deploy.

Lobby snapshots read open, active, and unseen finished matches in one SQL statement (`DailyMatch::list_lobby`), then partition by status while preserving each list's order. A claim or finish on another connection cannot put the same match in two lists or omit it between status reads.

Spectating: the Lobby modal lists other people's active matches under a `live games` section; opening one enters the same full-screen board read-only (`DailyBoardState::spectating`). Every roster game is spectatable; battleship shows only the public hit/miss record on both players' waters, never the fleets (see §4 / `battleship_ui`), and briscola shows both hands as backs (`briscola_ui`). Read-only is enforced three ways: a spectator is never `turn_user_id` (so `play_move`/`board_select_or_move` no-op), `board_resign` early-returns on `spectating`, and `resign` server-side bails "you are not playing in this match". Spectating has no data path of its own: `active_matches` is a global snapshot, filtered to "mine" per session.

Non-goals for v1 (deferred by decision): wagers/escrow, tournaments, draw offers (chess draws happen only via stalemate/repetition), quest wiring. The schema leaves room for all of them (§8).

## 3. Service And Persistence Model [STABLE]

- **No live actor per match.** Every mutation (`post_challenge`, `claim_challenge`, `cancel_challenge`, `play_move`, `resign`) loads the row, validates (chess: `chess_core::rules` over `state.fen`; battleship: `battleship.rs` over the stored fleets/shots; connect4: `connect4.rs` over the drop history), and persists. Nothing to reconcile after a restart. `play_move`'s shared prelude (active status, turn, deadline) runs before the per-game dispatch; a battleship "move" carries the target cell in `to`, a connect4 "move" the column.
- **Snapshot**: one global `watch::Receiver<Arc<DailySnapshot>>` (`open_challenges` + `active_matches` summaries with usernames resolved). Per-session UI filters for "mine". Republished on every local mutation and on every `daily_match_changed` notify, which a row-level trigger on `daily_matches` (migration 212, empty payload, the listener never trusts one) fires for every write that changes a row, on every replica: a claim, a move, a finish, its payout, a result ack, a sweeper forfeit. A guarded write that matches no row (the sweeper's forfeit on a quiet minute) sends nothing. So every replica holds the same snapshot within a notify's round trip; the sweeper loop republishes every 60s as the backstop for a lost notify or a re-read that failed.
- **Events**: `broadcast<DailyEvent>` of `ChallengePosted`, `ChallengeClaimed`, `MovePlayed`, `MatchFinished`, targeted `Error { user_id, message }` for banners (svc error strings lowercase; banners sentence case).
- **Row lifecycle**: `open -> active` (claim) `-> finished | cancelled`. Claim is a guarded UPDATE (`WHERE status='open' AND opponent_id IS NULL`) so two simultaneous claims can't both win; colors are random at claim time and stored in `state.colors`. A `finished` row keeps broadcasting: it rides the snapshot's `finished_matches` list until both players have acked (or the 30-day window lapses), with `mark_result_seen` flipping each player's own seen column exactly once (a repeat ack touches 0 rows and skips the republish).
- **State JSON**, one shape per game, all with a top-level `revision`: `DailyChessState` (version 1: `fen`, `colors`, `move_history` with SAN labels + timestamps, `position_history` for threefold repetition; shared verbatim by chess and chess960, which differ only in the opening `fen`. Every FEN is written in Shredder notation (`rules::fen`) so a shuffled back rank can name its rook files; the `KQkq` spelling still parses), `DailyBattleshipState` (version 1: two `sides` of `{user_id, ships, shots}`; ships are contiguous cell lists, shots carry hit + timestamp), and `DailyConnect4State` (version 1: `red`/`yellow` user ids + `drops` column history; everything else derived). `DailyMatch::update_state` and `DailyMatch::finish` share one exact compare-and-swap guard (`STORED_REVISION_EQ_SQL`): the write applies only while the stored `revision` still equals the one the caller loaded, so a superseded write updates 0 rows and the service surfaces "move was superseded". Exact equality (not `stored <= incoming`) matters because a battleship hit keeps `turn_user_id` on the shooter: the turn guard alone can't reject a duplicate same-revision write, so the CAS is what stops last-write-wins there. `update_state` also still guards on the expected mover/turn (a belt-and-suspenders check that also blocks off-turn writes). `resign` reloads and retries on a 0-row (superseded) finish, and stays game-agnostic by deriving the winner from the row and bumping `revision` on the raw JSON.
- **Deadlines are durable by construction**: `turn_deadline_at` is a DB timestamp, never an in-process `sleep_until`. `play_move` rejects a move once `turn_deadline_at <= now()` (and so never resets a dead clock); the sweeper (60s loop) is the forfeit executor for `status='active' AND turn_deadline_at < now()` rows (winner = other player, result `timeout`) and therefore survives restarts for free.
- **Finish payout**: `DailyService::pay_winner` (called from `finish_events`, awaited, not spawned). Gate 1 in Rust: `moves_played < DAILY_WIN_MIN_MOVES` returns `DailyWinPayout::Unplayed` without touching the DB. Gate 2 in the grant: `ChipService::credit_per_event_pair_day_reward_template(game.reward_key(), event_key = match_id, pair_day_key = "<loser id>:<created UTC date>")`, which is `GamePayout::grant_multi` over two `Unique` keys (`event` and `pair_day`) under one advisory lock, all rows or none. Templates are `claim_policy = per_event` (migrations 102-142). The match key keeps payouts idempotent (a sweeper retry never double-pays); the pair-day key is the cap. `credited = false` on a first finish is therefore the cap (`PairDayCapped`), because the match key cannot collide there. A credit error is `Failed`: logged, the match still finishes. Every outcome is one `late_ssh_daily_win_payouts_total{outcome}` count (`metrics::record_daily_win_payout`) and is written to `daily_matches.win_payout` (`DailyMatch::set_win_payout`, a second UPDATE after the finish, by design: the payout is decided once the finish is durable, and a failed credit must never un-finish a match; a failed write of the column loses only the result-row phrase and is logged). The column is CHECKed to the four `DailyWinPayout::db_str` spellings, NULL for draws and pre-gate rows.
- Results: `checkmate`, `draw`, `fleet_sunk`, `four_in_a_row`, `most_discs` (reversi), `no_moves` (checkers win by block/capture), `borne_off` (backgammon), `most_points` (briscola), `eight_potted` / `early_eight` / `nine_potted` / `frame_won` (pool), `pegged_out` (cribbage), `reached_hundred` (gin rummy), `resign`, `timeout`, `''` while running. Cribbage and gin rummy cannot draw. Battleship and backgammon cannot really draw (backgammon's stall cap is a defensive `draw`); connect four, reversi, and checkers can draw (winner `None`, no payout, like chess draws).

## 5. Notifications [STABLE]

- **Your-turn desktop notify**: `DailyState` holds a cloned `notify::Notifier` and pushes `Notification::daily_your_turn(opponent)` (`Kind::GameEvents`) on the became-my-turn edge while connected. Edge detection: `turn_notified_match_ids` is seeded from the login snapshot (connecting never notifies; the panel's glow + your-turn rows are the on-login nudge) and pruned when the turn passes away, so a turn coming back is a fresh edge.
- **Finish banners**: `MatchFinished` carries `DailyFinishOutcome` (`Won { user_id, payout }` / `Draw`) and banners all three outcomes for connected players: winner `Banner::success` with what the chips did (`+500 chips`, or `no chips: under 5 moves`, or `no chips: one paid win per opponent per game per posting day`), loser `Banner::info` (`you lost the match (timeout)`), draw `Banner::info`. `Banner::info` / `BannerKind::Info` (amber, `•` icon) exists for exactly this: bad news isn't an error. Offline players are covered by the durable result rows (§4), not by banners. There is deliberately no finish desktop notification in v1; the lingering row is the nudge.
- **#lounge result line**: a finished match posts one system line to #lounge via the standard activity path (`ActivityKind::DailyResult` → `filter::lounge_includes` → `activity/lounge.rs`), NOT a bespoke `DailyEvent`/ghost-bot path. See §1. Only finishes publish; posting and claiming stay silent, and there is still no quest wiring.

## 6. Critical Invariants [STABLE]

- Daily matches never touch the house-table runtimes; house tables never reach into `daily_matches`. The only shared code is `chess_core` (and `ChipService`). `DailyService` and `HouseTableRegistry` stay separate services: no unifying trait, no `GameSurface` abstraction.
- The game roster is `games.rs::DailyGame` and nothing else: no game-kind string comparisons outside `DailyGame::from_kind`/`kind()`. Rows whose `game_kind` this build doesn't know are hidden from the snapshot (and skipped for payout with an error log), never guessed at.
- `DailyGame::win_payout` is display-only; the seeded reward template pays. Keep them equal.
- The lobby is not a faucet. Every win credit goes through `pay_winner` and its two gates; no finish path credits chips on its own. Known and accepted: the pair-day cap bounds one pair at one win per game per posting day, not one account. A colluding pair's ceiling is one paid win per roster game per direction per day (about 5,800 chips each way, and they have to play all thirteen games), and five alt accounts are ten pairings. If Top Chips ever looks wrong, group `chip_ledger` daily-win rows by `(winner, opponent)` over 30 days; a per-account daily quota would need a counting arm on `GamePayoutKey`, deliberately not built.
- **Known, not fixed: the finish path nests pool connections.** Every play path, `resign`, and `sweep_expired` hold their pooled `client` across the awaited `finish_events`, which takes a second connection for the grant (`pay_winner`) and a third for `set_win_payout`. The pool is 16 with a 5s wait (`late-core/src/db.rs`), so enough simultaneous decisive finishes could starve it; the grant would then time out, fold into `DailyWinPayout::Failed`, and the win stays unpaid with `win_payout = 'failed'` on the row (recoverable by hand from that column, never silently). Left as is because correspondence finishes are a few a day. Fix when the lobby gets busy or when the wager rewrites these paths: pass the held `client` into `pay_winner` / `record_win_payout`, or drop it before the await and re-acquire for `publish`.
- Claim stays a guarded UPDATE; never split it into read-then-write without the status/opponent guard.
- Deadlines stay DB timestamps. Do not introduce in-process timers for correspondence deadlines; a `sleep_until` clock does not survive restarts and this domain must.
- The entry cap (`DAILY_MAX_ACTIVE_ENTRIES`, 10) counts open challenges posted plus active matches played, enforced server-side on post AND claim. It exceeds the panel's `MATCH_SLOTS` (4) by design: the panel is a top-4 view (your-turn rows first, nearest deadline within), so the actionable matches always hold the slots while waiting rows and any overflow live in the Lobby modal, which shows the full set. Unseen finished results never count against the cap; in the slots they displace waiting rows, never your-turn rows, and clear on first look.
- Result acknowledgment is per-player and only ever touches the acker's own seen column; nothing may ack on another player's behalf, and merely opening the modal must not ack (only leaving the board or an explicit `x`).
- `state.revision` only increases; superseded writes must fail loudly ("move was superseded, reload the match"), not last-write-win.
- Panel height is constant (6 rows); empty slots render dashes. Never collapse or grow the panel between states. The #lounge strip is the one surface allowed to come and go, because coming is its signal; while up it is 9 rows or 1, chosen by the card's size only, and it never announces an empty lobby.
- The live board carries positions only. A `LiveBoard` for a hidden-information game must stay what a spectator may see; adding a game means adding its `MatchSummary::of` arm, which is exhaustive over `DailyGame`. `LiveBoard` has one variant per board shape, not per game (the three pool games share `Pool`), and its renderers are exhaustive over it.
- Match chat is open to whoever is watching: the two players are members from the claim transaction, and a spectator joins lazily when the board opens (`App::tick`, off `board_match_chat_room_id`). Membership is the auth for tails and sends both, so the pane follows it: `DailyBoardState::shows_chat` draws chat for a player always, for a spectator only once `chat_joined`. That is the whole gate; no surface may re-derive it.
- Chat rides the match lifecycle: created at claim (never at post), reaped 30 days after finish/cancel by the sweeper. Every surface must tolerate `chat_room_id = NULL` (pre-109 matches, post-reap rows).
- The backtick cycle is Home chat + your-turn boards + seated house tables + unfinished Arcade dailies (`app/workspace/arcade.rs`, one stop per `DailyPuzzle`: today's daily boards with player moves, not solved, never real-time games or personal boards). Do not re-add rooms stops; new workspace kinds go through the `GameWorkspace` enum.
- The ONLY activity daily games publish is the finish result line (`ActivityKind::DailyResult`, §1/§5): one per match, on finish only, never on post/claim. No other `ActivityEvent`, no direct chat writes, no quest signals. New games inherit this automatically: `finish_events` is the single choke point and `DailyGame::display_name()` is a required exhaustive method.

## 8. Future Hooks [VOLATILE]

All deliberately pure additions with no schema impact unless noted:
- #lounge announcements go through the standard `ActivityEvent`/`filter::lounge_includes` path (finish result line, §1/§5). Quest wiring is open and would hang off `DailyEvent::MatchFinished`.
- Wager escrow: not planned, not built. The sketch: a `wager` column, hold on post and match on claim in `ChipService`, stakes from a fixed list, winner takes the pot minus a 10% burn, draw and cancel refund, timeout pays the winner. There is no loser consolation: 100 chips could not be a wage without reopening the faucet.
- Seeded arcade score duels: same table (`game_kind='duel_snake'` etc.), `state` holds seed + submitted scores, sweeper settles at deadline.
- Spectating covers every roster game (see §4). Still open: a spectator count / "N watching" signal, and (if ever wanted) revealing battleship fleets to spectators once the match ends.
- 1d/3d deadline choice, rematch one-key, draw offers: all raised in the FRD as cheap follow-ups if requested.
- Roster: durable server randomness comes in two shapes, backgammon's stored rolls (`turns: [{roll, hops}]` + `next_roll`) and the multi-hand card games' appended deals (`deals` + `deal_next`); a future randomness-bearing game reuses whichever fits.
