## 0. Context Maintenance Protocol [STABLE]

Read this after root `CONTEXT.md` whenever a task touches daily matches, challenges, the game roster, the Daily Games sidebar panel/modal/boards, or the `daily_matches` table.

- Update this file when the match lifecycle, deadline policy, cap, payouts, the game roster, or UI surfaces change.
- Update root `CONTEXT.md` when global keybindings, the screen list, or the data model change.
- Chess rules/rendering primitives are NOT owned here: they live in `app/games/chess_core` (see `app/games/CONTEXT.md`). Battleship, connect four, reversi, checkers, backgammon, and briscola rules ARE owned here (`battleship.rs`, `connect4.rs`, `reversi.rs`, `checkers.rs`, `backgammon.rs`, `briscola.rs`): no other surface plays them. Pool is the other exception alongside chess: its physics, rulesets and renderers live in `app/games/pool_core`, and `pool.rs` here is only the match wrapper. Briscola draws its cards with the shared `app/games/cards.rs` renderer but owns its own rank set, since briscola's rank order and card points generalize to no other game.
- `mod.rs` stays declaration-only.

### Adding a game to the roster

`games.rs` is deliberately one enum, no trait objects. Add a variant to `DailyGame` and the compiler walks you through every exhaustive match: DB kind string (`DailyMatch::GAME_KIND_*`), lowercase command `label`, title-cased `display_name` (the #lounge result line uses it), win payout, reward key, ledger reason, tagline. A game with per-player hidden state (like battleship's fleets or briscola's hands) also owes a hidden view in its board renderer for both the opponent and spectators (see `battleship_ui::spectate_waters_lines`, `briscola_ui`). Beyond the enum you owe: a state module (serde state + pure rules, like `battleship.rs` / `connect4.rs`), a `claim_challenge` initial-state arm and a `play_move` dispatch arm in `svc.rs`, a `DailyGameDetail` variant + board input ops in `state.rs`, a board renderer (like `battleship_ui.rs` / `connect4_ui.rs`), a `publish()` move-count arm, and a migration seeding `daily_<game>_win_payout` in `reward_templates` (plus the key const in `late-core/src/models/reward.rs`). The displayed prize (`DailyGame::win_payout`) and the seeded template's `reward_chips` must stay in sync — the template is what actually pays.

A **variant** of a game already on the roster is much cheaper: chess960 is a second `DailyGame` arm over the same state type, detail struct, rules and renderer, so it owes only the enum arms, a claim arm choosing its opening position, a `DailyGameDetail` variant holding the same detail struct (so `kind()` stays honest), and its reward-template migration. Reach for that only when the two games really are one game with different setup; anything with its own rules gets its own module.

The compiler cannot demand everything. Grep-hunt these seams too: the result string's arm in `board_ui.rs::result_banner` (falls back to "Finished" silently), the challenge copy in `app/help_modal/data.rs` (static strings enumerate the roster), the `board_move_cursor` wildcard arm, the mouse hit-test arm in `board_input.rs` (each game interprets `target_geometry` its own way), and this file.

**Move channel.** Most games' move is a single cell/column: `play_move(from, to)` carries it (chess uses both, battleship/connect4/reversi pack it into `to`), and `board_select_or_move` dispatches per `DailyGame`. Checkers and backgammon are the exceptions — their moves are variable-length sequences, so each rides its own channel end to end: `svc::play_checkers_move_task(user_id, match_id, path: Vec<usize>)` → `play_checkers_move` (shares `move_prelude` with `play_move`, which now only turn/deadline-guards) → `play_checkers`, and `svc::play_backgammon_move_task(user_id, match_id, hops: Vec<backgammon::Hop>)` → `play_backgammon_move` → `play_backgammon`; the client builds the checkers path in `CheckersDetail.pending` (`state.rs::checkers_select`, prefix-matching legal moves so multi-jumps chain click-by-click) and the backgammon turn in `BackgammonDetail.pending` + `selected` (`state.rs::backgammon_select`, lift a checker then land it, hop by hop against the legal-turn prefixes), with Esc clearing either via `cancel_pending_move`. Reversi and checkers are cell-cursor games (row 0 drawn at the top like battleship, `target_geometry` maps a click to a cell); the `board_move_cursor` and `board_input` mouse arms handle both 8x8 boards together. Backgammon's cursor instead walks a visual 2x14 slot grid (six points, the bar, six points, the off tray, twice) that `backgammon::slot_target` resolves to a point/bar/off from the viewer's seat; its mouse arm divides `target_geometry` into the same slots.

## 1. Summary [STABLE]

A daily match is a relationship between two people, not a place: no seats, no ready-up, no AFK timers, no live actor per match. What is shared with table chess is the chess itself, through `app/games/chess_core`; every other roster game's rules live entirely in this domain.

Match chat + voice (added 2026-07-13): a claimed match DOES get a chat room — a private, two-player `chat_rooms(kind='game', visibility='private', auto_join=false)` row (slug `daily-{match_id}`, `game_kind` = the roster kind string) plus an enabled `voice_channels(target_kind='chat_room')` (display name `{game label}: {challenger} v {opponent}`), all created inside the claim transaction with both memberships (`ChatRoom::create_daily_match_room`); `daily_matches.chat_room_id` (migration 109, `ON DELETE SET NULL`) links them. `kind='game'` buys the existing hidden-from-rail / no-Mentions / no-IRC behavior; `visibility='private'` plus membership-as-auth keeps it players-only, and `ChatService::join_game_room` rejects non-members for private game rooms. Chat attaches to the match, not the game, so new roster games inherit it with zero per-game code. Open challenges have no chat (nobody to talk to); matches claimed before migration 109 have `chat_room_id = NULL` and render without the pane. Chat rooms + voice channels are reaped by the sweeper once a match has been finished/cancelled 30+ days (`DailyMatch::delete_stale_chat_rooms`, hourly cadence on the 60s loop) — aligned with the unseen-result window. There is deliberately no unread-chat signal in v1: the your-turn glow is the nudge, and opening the board marks the room read.

Core shape:
- **A roster of games, one enum.** `games.rs::DailyGame` (chess, chess960, battleship, connect four, reversi, checkers, backgammon, briscola, eight-ball, nine-ball) owns every per-game fact: `daily_matches.game_kind` string, label, win payout, reward key, ledger reason. Challenge posting picks a game (the Lobby's `c`/`C` draft picker); everything downstream dispatches on it. See §0 for the add-a-game checklist.
- **Open lobby is the centerpiece.** Anyone posts an open challenge; anyone claims it; claiming starts a match. Open challenges persist until claimed or cancelled (no expiry in v1). Directed challenges are the same row with `target_user_id` set.
- **24h per move, fixed in v1.** Missing the deadline forfeits (sweeper, §3).
- **Cap: 10 active entries per user** (`DAILY_MAX_ACTIVE_ENTRIES`): open challenges you posted plus active matches you play in, combined. This exceeds the panel's 4 match slots on purpose (raised from 4 on 2026-07-12): the sidebar is a top-4 view of the most actionable matches (your-turn first, nearest deadline within), and the full set is always visible in the Lobby modal. (History: was 5, lowered to 4 on 2026-07-09 to match the slots exactly, then raised to 10 once the panel became an explicit top-4 view.)
- **Winner payout** through the existing reward-template path, one `per_event` template per game: `daily_chess_win_payout` 500 chips (migration 102), `daily_chess960_win_payout` 500 chips (migration 142), `daily_battleship_win_payout` 300 chips (migration 105), `daily_connect4_win_payout` 400 chips (migration 106), `daily_reversi_win_payout` 400 chips (migration 115), `daily_checkers_win_payout` 400 chips (migration 116), `daily_backgammon_win_payout` 400 chips (migration 117), `daily_briscola_win_payout` 400 chips (migration 128), `daily_eightball_win_payout` / `daily_nineball_win_payout` 400 chips each (migrations 176/177). Prizes are shown on lobby rows and in the challenge draft; `DailyGame::win_payout` is the displayed number and must match the seeded `reward_chips`. **Two gates on the payout** (decided 2026-08-27): a win pays only if at least `DAILY_WIN_MIN_MOVES` (5) half-moves were played (a resign is not a move; a timeout counts the moves that were made), and at most one win per opponent per game per UTC day the match was **posted** (not finished) is paid: the `pair_day` claim carries the template's `game` like every claim row, so chess and battleship against the same person on the same day both pay (decided 2026-08-27). Keying on the posting day is what keeps honest play whole: two long games against the same person posted on different days both pay whichever day they end. A refused win finishes the match normally, posts the #lounge line, tells a connected winner in the banner why no chips came, and stores the reason in `daily_matches.win_payout` for the lingering result row (`you won · resign · no chips, under 5 moves`).
- **#lounge result line (the one activity daily games publish).** When a match *finishes* — and only then, never on posting or claiming — `finish_events` fires one `ActivityPublisher::daily_result_task`, and emits a single `ActivityKind::DailyResult { game }` event: `won a game of {Game}` for a decisive result (attributed to the winner, naming only them — the loser is never resolved, so the feed never shames whoever lost) or `drew with {other} at {Game}` for a draw (a draw shames no one, so both players are named). `filter::lounge_includes` approves it, so it posts to #lounge as a system line (one per match). The game name is `DailyGame::display_name()` (title-cased: "Chess"/"Battleship"/"Connect Four"), a required exhaustive method distinct from the lowercase command `label`. Chips remain the only *economy* footprint (no quest integration); `DailyService` holds an `ActivityPublisher` solely for this line.
- **Chess960 rules:** ordinary chess from a shuffled back rank. One of the 960 legal openings is rolled at claim time (`chess_core::rules::random_chess960_board`: bishops on opposite colours, king between its rooks, Black mirroring White) and lives on in the stored FEN; nothing after move zero differs from chess, so the state type, rules kernel, board renderer, results, and 500-chip payout are all the chess ones. The one thing a player notices: **you castle by moving your king onto your own rook**. The lichess-style two-square push is only offered when the king happens to start on e1/e8, because from anywhere else that same pair is an ordinary king step (see `app/games/CONTEXT.md`).
- **Battleship rules (v1):** both fleets (5/4/3/3/2) are placed randomly at claim time — a placement phase would cost a whole correspondence day — the coin flip picks the first shooter, one shot per turn on a 10x10 grid, a hit fires again (deadline still resets), sinking all five ships finishes with result `fleet_sunk`.
- **Connect four rules:** 7x6 grid, the claim-time coin flip picks who's red (red drops first), one drop per turn, the turn always passes. Four in a row finishes with result `four_in_a_row`; 42 drops with no line is a `draw`. The state stores only the drop history — grid, turn, and move count are derived, so the state can't self-contradict.
- **Reversi rules:** 8x8 Othello, the claim-time coin flip picks who's black (black moves first), one disc per turn, a legal move must flip at least one bracketed opponent disc. A player with no legal move is auto-passed (passes are NOT stored — `turn()` resolves them by replay, so `next_turn` can come back to the mover). Neither side able to move finishes it: most discs wins (`most_discs`), an equal split is a `draw`. State stores only the placement history from the fixed four-disc opening; board/turn/counts are derived.
- **Checkers rules:** 8x8 American draughts on the dark squares, the claim-time coin flip picks who's red (red moves first, up the board). Captures are mandatory (a jump chain is played to completion — a partial chain never matches a legal move), a man crowned on the far rank ends the turn at once, and reaching the back rank makes a king. Blocking or capturing every enemy piece finishes it (`no_moves`); the forty-move rule (no capture, no man move) is a `draw`. State stores only the move history (each turn a path of squares); there are no passes — a side with no move simply loses.
- **Briscola rules (the roster's first hidden-hand game):** two players, 40 cards (a standard deck minus the 8s/9s/10s), three each, the next card turned up as the trump and left under the stock so it is the last card drawn. The claim-time coin flip picks seat 0, who leads the first trick. There is no obligation to follow suit: the leader plays anything, the follower answers with anything, and the trick goes to the highest trump, else the highest card of the led suit (A > 3 > K > Q > J > 7 > 6 > 5 > 4 > 2). The winner draws first, then the loser, then leads. 120 points are on the table (A 11, 3 10, K 4, Q 3, J 2) and passing 60 settles it, so `apply_play` finishes the match the moment either side is past 60 (`most_points`); 60-60 after all twenty tricks is a `draw`. The state is the connect-four pattern taken further: `{deck, plays}` and nothing else. The deal is the match's entire supply of randomness (contrast backgammon's per-turn server rolls), so every draw is a replay of a fixed order and `table()` derives hands, turn, scores, and trick history from the history alone. **Hidden information is a rendering rule, not a data one:** the state holds both hands and the stock, exactly like battleship holds both fleets, and `briscola_ui` is the only thing standing between them and the screen. It draws faces for the viewer's own hand only, backs for the opponent's, and no faces at all for a spectator. That is safe because the TUI renders server-side over SSH; there is no client to leak to. Both captured-point totals are shown throughout, a deliberate deviation from the table game, where counting only your own pile is part of the skill: across a move-a-day match that stops being memory and becomes note-taking.
- **Backgammon rules:** standard board, no doubling cube (the payout is the fixed reward template), the claim-time coin flip picks who's white (white plays first with a server-rolled non-double opening). One turn per day: the stored `next_roll` is played as hops (doubles = four), bar checkers enter first, maximal dice must be used (higher die when only one plays), lone checkers are hit to the bar, bearing off needs the whole side home. First to bear off all fifteen wins (`borne_off`). The state is the NEW pattern: `turns: [{roll, hops}]` — dice are durable server rolls stored per turn, forced passes are recorded as turns with no hops (so turn = parity), and `roll_next` (server-only) rolls for the next mover after each move, auto-recording passes until someone can play; a defensive stall cap (100 straight passes) draws a theoretically-wedged match. Clients applying a turn optimistically never roll — `next_roll` stays empty until the reload lands.
- **Pool (eight-ball and nine-ball, added 2026-09-09):** the roster's only simulated game, and the one place the "a variant is one game with different setup" rule bends. 8-ball and 9-ball are **two `DailyGame` variants sharing one state type (`pool.rs`), one detail struct and one renderer, but with separate rulesets** — their rules genuinely differ, so `PoolRules` is a field on the state rather than a second struct. Everything below the ruleset (table, rack format, physics, shot, renderers) is shared and lives in `app/games/pool_core`, so a live pool hall as a house table would reuse it verbatim.
  - **The physics is the referee.** A shot is `(optional placement, azimuth, tip offset, speed, called pocket)` and nothing else; the server re-simulates it from the stored rack. A doctored client can send an illegal *shot* and never an illegal *result*. This is also why pool is the one roster game with **no optimistic apply**: every other game can work out its own result locally, but a pool result is a simulation, and running it on two machines to see whether they agree is exactly the coupling this split avoids. The board waits for the reload; `PoolDetail::shot_in_flight` blocks a second shot in the meantime.
  - **What is persisted:** `rack` (where the balls are now, authoritative), `prev_rack` (where they were before the last shot), and the `Shot` inputs. `prev_rack` is exactly enough to re-simulate and animate the last shot, which is the only shot anyone watches; a full timeline would be megabytes of JSONB per move. The table preset is stored **by name** and resolved through `table::preset`, so retuning a coefficient surfaces as an error on the match that needs it rather than silently reinterpreting a rack that was never played on that equipment.
  - **Potting keeps the table** (battleship's "a hit fires again"). That is what stops a rack costing as many days as it has balls: a present player runs out in one sitting and only a miss hands the clock over. One rack per match — race-to-N is deliberately not in v1.
  - **Ball in hand rides inside `Shot.place`**, so a foul costs the fouled player no extra turn of the correspondence clock. A potted cue ball makes placement *mandatory*: `sim::simulate` un-pots the cue ball unconditionally, so without that check a scratch would quietly resurrect it at the pocket mouth. `ShotMode::Place` (`m`) is how a player sets it down, and a scratched board **opens already holding it** rather than looking broken. **Any foul opens the board already holding the ball** — every foul in both rulesets grants one, not just a scratch (no contact, wrong ball first and no-rail all do), and a player who is not told they have it plays the leave they were left. A left click sets it down *and* ends the mode (`place_and_commit`), because left click means "there, done" everywhere else on this board. A cue ball that was actually potted also starts at a legal spot near the break spot rather than nowhere, so the board is never showing a table with no cue ball on it. A click **snaps to the nearest legal spot** through `rules::free_spot` instead of being refused — the table view is an overview where a ball is a few pixels, so an exact click is not something a player can be asked for. The held ball is drawn at its pending spot (`pool_ui::held_ball_frames`), because the one thing a player needs while placing it is to see where it will land — and it **follows the pointer live** while `Place` is armed (`pool_hover_table`, fed from `board_input` because only the caller can turn a cell into a spot on the cloth). It is the one mode the pointer steers *through the table geometry* rather than as a bare delta; `PoolDraft::pointer_moved` therefore reports `Ignored` for `Place`.
  - **Nothing about a shot is sequenced** (changed 2026-09-09, replacing an earlier four-stage wizard). Target, spin, aim and stroke are all live at once and the player may strike whenever they like; a key only says what the *pointer* is steering right now (`ShotMode`). `[`/`]` cycle the legal targets and `'` jumps to the lowest one that is on; a click picks any spot on the cloth; `a` arms aim, `e` arms spin, `m` takes ball in hand, and `x`/`s`/`w` arm the stroke light, normal or strong. Three gestures, three meanings:
    - **Left click commits** — keep the adjustment, put the cue down. Space is its keyboard twin. It is taken on the *release* and only when the press did not travel, because a press that moves is a **re-grip**: the mouse lifted off the pad, the reference following the pointer while the setting stays put. That is the only way to keep turning an aim once the pointer has run out of screen (a terminal reports motion only inside its own window), and until the button comes up there is no telling the two gestures apart.
    - **Right click resets** — zero what is armed (centre ball, dead-on aim, the held ball back on its opening spot) and *stay in the mode*. With **nothing** armed it clears the whole shot: aim and spin both back to square. That case is the common one and it was the one missing — you look at the panel, decide against the english, and there is nothing to re-arm and undo because you already put the cue down. `c` is the keyboard twin. "Put the spin back to centre" is what a player reaches for far more often than "undo the last few pixels", and centre-ball is fiddly to walk back to on a face a few pixels across. A stroke has no meaningful neutral, so there it just puts the cue down.
    - **Esc cancels** — restore the value the mode was armed with and drop the mode. All three adjustable values come back from one snapshot taken at arming time, so a snapshot can never fall out of step with the mode it belongs to; arming a second mode commits the first and re-snapshots, so a cancelled spin cannot undo a settled aim. With nothing armed, Esc leaves the board like every other game.

    **The aim has two axes**: the pointer's left/right picks which side of centre, up/down how far off it (`spread_aim`). The second exists because a pointer runs out of screen long before an aim runs out of range — a player aiming from the right-hand side of the board had nowhere left to push, and the re-grip alone was not enough. Coming back in stops dead at centre rather than sliding through to the far side of the ball, which nobody asks for and cannot be aimed at. The arrows carry the same pair.

    The hint row is rewritten from `ShotMode::hint`, which lives beside the enum in `pool_core` so the controls and the description of them cannot drift.
  - **The cue panel is laid out as the shot, so its zones are the modes** (added 2026-09-10). It draws the target ball at the top, the cue ball in front of you, and the cue below — so a click on the target ball or the sighting line arms *aim*, a click on the cue ball's face places the tip and commits *spin* in one gesture, and a click on the cue arms the *stroke* at the middle band. `cue_ui::draw` returns a `PanelHit` with all of that geometry and `board_input::click_cue_panel` reads it, so the hit test never reconstructs the panel's own layout. A press while a band is already armed is part of the pull and never a mode change. This is what lets a player who has read nothing start a shot: the picture tells them where to click.
  - **Why modes and not held keys.** A terminal sends key *presses* only: there is no key-up event without the Kitty keyboard protocol, which this build does not enable (`input.rs`), so "hold `a` and move the mouse" is not observable. Autorepeat is not a substitute — the first repeat lags half a second, the rate is a per-user OS setting, and SSH jitter smears it. What *is* available is bare pointer motion: `?1003h` any-event tracking is already on (`state.rs`), so the mouse steers the armed mode with no button held. Buttons are still needed for what a motion stream cannot express — picking a spot, committing, cancelling, and letting go of the cue. Right click is already load-bearing elsewhere in the app (Minesweeper flags, Solitaire auto-move, the Artboard's pan), so it is known to survive real terminals.
  - **The stroke is the real gesture: draw the pointer down, then push it back up through the ball.** Crossing the point where the stroke began is the moment of contact — no button anywhere in it. Two consequences worth keeping: the power is the deepest point of the **backswing**, not the pull at the instant of crossing (on a real table how far you drew back is what decides the shot; how the follow-through is timed is not), and a minimum backswing is required so that nudging the mouse upward on an armed cue cannot fire it. The stroke is also the one mode where pointer motion is read as an **absolute offset from where the gesture began** rather than as a delta — there the origin means something physical, it is where the cue ball is. Space fires from the keyboard, and arms the normal band first if nothing is armed, so the least-informed possible keypress still plays a sensible shot. `PowerBand` scales the same pull into a different speed: the pointer's whole travel is spent inside the range the player asked for, instead of putting a delicate safety and a hard break a few pixels apart. **The bands are pinned to how hard people actually hit** rather than spread evenly over the range — a full pull in `normal` is ~4.3 m/s, a firm pot, not the two thirds of a break the first cut gave it, which made every shot feel like a slam. And the cue **stays thrown through the ball** from the moment the stroke registers until the shot has finished playing (`CueView::follow_through`, driven off `shot_in_flight || playback`, so there is no timer to fall out of step): a cue that snapped back to rest looked exactly like a stroke that never took.
  - Keyboard alone is enough for all of it (arrows drive whatever is armed, `h`/`l` and `H`/`L` walk the aim by hand), which matters because the client's keyboard-only interaction mode ignores the mouse entirely. The mouse is the better path, not the required one, and is the only way to pick a cushion.
  - **The cue ball's face is drawn magnified**: the whole drawn ball is the half-radius the tip may actually use, so the miscue circle is the ball's own edge and a click at the edge is the limit. A true-to-life face would spend most of a ball a few pixels wide drawing the region nobody is allowed to strike. The pointer rates (`TIP_PER_COLUMN`/`TIP_PER_ROW`) were halved to match, so the magnification buys precision rather than speed.
  - **The opponent's aim is broadcast while they compose it** (added 2026-09-10). `DailyEvent::AimChanged` carries a `PoolAimShare` — target, aim, spin, pull, mode, placement, called pocket — over the *existing* in-process broadcast channel; `DailyService` is already process-global, so this needed no new plumbing and no new table. **The one event on this domain that is not a move**: everything else reports something durable, this reports what somebody is thinking about. Not persisted, not acknowledged, and a dropped event costs nothing because the next one carries the whole state. Publishing goes through one funnel (`board_input::handle_event` → `pool_publish_aim`) so a new control cannot be one forgotten line away from being invisible; `should_share_aim` throttles it to 120ms *except* on a mode change, since "they have armed the stroke" is the update whose timing is the information. The renderer always draws from a share (`PoolDraft::watching`), local or remote, so the two paths cannot drift.
  - **`v` swaps the overview for the shooter's eye** (`pool_core::table_3d`, added 2026-09-10). It is a *camera*, not a control: allowed while watching, waiting or spectating, and while a shot plays out the eye stays where the shooter stood rather than following the ball — a camera that chases the cue ball round the table is not what watching a shot looks like. The view preference lives on `DailyBoardState`, not the detail, so it survives the reloads that rebuild the detail. The eye is render-recorded (`pool_eye_geometry`) exactly like the overview's rect, and `table_point_at` inverts whichever of the two was actually drawn — two views on one board is two chances for a click to land somewhere the picture did not put it. A click above the horizon is the room, and commits like any other click off the cloth.
  - **Animation** is the daily board's only one. **A reload carries a running playback across** (`PoolDetail::adopt`): a reload rebuilds the detail from the row and a fresh one has no playback, so a reload landing mid-animation deletes the animation. The shot that *ends* a rack publishes two events — `MovePlayed` and `MatchFinished` — and each asks for a reload, so the first started the shot playing and the second wiped it milliseconds later; every other shot publishes one event and survived by luck. That is what made a rack look like it ended with no final shot. It runs for `Timeline::visible_duration`, not the physical duration: friction is asymptotic, so a shot's last stretch is balls creeping fractions of a millimetre, and played back in full that is seconds of a table that looks settled while the board still refuses a shot. The status line also says `▶ the shot is playing` outright while it runs, because a player reading "Your shot" while nothing responds concludes the board is broken. Playback starts on **reload** for both players through one code path (`start_pool_playback`), gated on a shot count the board has not shown yet; the first load seeds that count so opening a match shows the table as it stands rather than replaying the shot that happened before you arrived. While a shot rolls, `wake_hint` returns `HOT_TICK` — the single change pool makes outside the daily and games domains.
  - **The table's border says whose board it is and whether it is live**, in two channels: hue is the turn (green yours, red theirs, dim for a spectator or a finished rack) and brightness is whether anything can be done (bright at the table, dimmed while the balls roll). It is **always drawn**, so the table never changes size as the state changes — the version that appeared and vanished made the whole board jump. It pairs with the `▶ the shot is playing` status line: between them there is no moment where the board's state is ambiguous. **That line outranks the result banner**, because the shot that ends a rack is exactly the one where announcing early is wrong — a pot is not a win until the rest of the shot has played out, since the cue ball can still follow the money ball down and hand the rack to the other player.
  - **The Lounge has a pool table** (`clubhouse::map::POOL_TABLE`, under the poker table). Enter on it opens the Lobby on the challenge picker with eight-ball selected, through `begin_challenge_draft_for` — walking up to a pool table is asking for pool, not for a list. It still opens the picker rather than posting outright, so the variant and the prize are in front of the player before anything is committed.
  - **The cloth carries a table's markings** (added 2026-09-10): the baulk line, the D behind it, and the head and foot spots. Cosmetic except the baulk line, which is drawn from `rules::head_string` — the same number the kitchen rule is enforced against, so a player put in hand after a break scratch can see where "behind the line" ends.
  - **The equipment gives back what the terminal takes.** The bar box's pocket mouths are a tenth over life size (4.95 / 5.5 inches): aiming through a terminal costs a player accuracy the equipment never took from them, since a ball is a few pixels and the pointer moves in whole cells. Pockets are also *drawn* from the mouth width rather than from the exaggerated ball, so retuning a mouth changes how a pocket looks and not only how it plays — and every one of them straddles the table's edge, corners included (see `app/games/CONTEXT.md`).
  - **Naming a pocket** is a click on it, or `p` to step through them, and it only answers while `requires_call()`. Nothing wrote `called_pocket` at all until 2026-09-10, and `apply_shot` *refuses* an uncalled shot on the eight — so eight-ball reached a position where every shot was rejected and no gesture would fix it. The same shape as the ball-in-hand dead board, and missed the same way: every test built a `Shot` by hand rather than going through the draft.
  - **Snooker (added 2026-09-10) is the third ruleset on the same state type**, and the one that justified the shape: `Ruling` has carried `points` and `balls_to_spot` from the start for exactly this. A full frame on a 12ft table, so `TableSpec` gained `head_string` and `d_radius` (a snooker baulk line is not a quarter of the table) and `BallInHand::TheD` (in hand from a semicircle, not from the whole baulk end). The state gained `scores`, `on_colour`, `free_ball` and `may_return`, all `#[serde(default)]` so pool rows still parse. **A frame can end level**, which no other game here can do, so `finished` is separate from `winner` and the service maps the pair onto a draw. Pockets are cut to the bar box's generosity rather than a real snooker table's — a real one is *tighter* relative to the ball, and tight pockets on a table drawn a hundred columns wide would make the game about the rendering. Ball exaggeration needed no per-table calibration in the end: it is a fixed pixel boost over true size, so a snooker ball being smaller *and* on a longer table is handled by the same arithmetic as everything else.
  - **`DailyGame::is_pool()` is the roster's one answer to "is this a cue game"**, and `DailyMatchDetail::pool()` / `pool_mut()` are the detail's. Every site asks one of those rather than spelling the variants out: snooker shipped for a single commit with a hand-written list in `board_input::is_pool_board` that had not heard of it, and because that one gate fronts *every* pool key and *every* pool click, the board was completely dead — no aim, no target, no stroke. A roster variant left out of a list that fronts an input layer is not a missing feature, it is an unplayable game.
  - **A snooker frame opens with the cue ball in hand in the D**, which is a rule rather than a nicety: where you break from decides what the pack does. `opening_placement` starts from a spot *inside* the zone on offer (`rack::d_spot` for the D), because `free_spot` walks outward from where it is pointed rather than hunting the table.
  - **Play-again rides on `Shot.play_again`** rather than a second move channel: it *is* the move — it takes the turn, joins the history and resets the clock — it just never reaches the simulator. `y` sends it, and it is refused unless the last shot actually fouled.
  - **Bar rules, not league rules.** Only the eight is called (calling every shot is a whole extra input step per turn); the eight on the break is spotted rather than won or lost on; a scratch on the break gives the kitchen. Nine-ball leaves out push-out and the three-foul rule, both additive later. Results are their own strings because "eight potted" over a loss would read as a win: `eight_potted`, `early_eight`, `nine_potted`.
  - **`DAILY_WIN_MIN_MOVES` (5) can refuse an honest win** — a nine-ball golden break pays nothing. Accepted: it is the same gate every roster game lives under.
- Three UI surfaces, one system of record: the passive right-sidebar panel, the Lobby modal (`Ctrl+G`, all interaction; "Lobby" is the user-facing name for the whole daily surface), and the full-screen board (`Screen::DailyMatch`, entered only from the modal; renders the match's game).

Unseen results (added 2026-07-12): a finished match stays visible to each player until that player has seen the result, because a correspondence loss (especially a timeout) usually lands while its loser is offline. Acknowledgment is per-player and durable (`challenger_result_seen_at`/`opponent_result_seen_at` columns, migration 108): opening the board and leaving it acks, `x` on the modal row acks without opening, merely opening the modal does NOT (results are news, not liquidity — skimming past must not clear them). Unseen results never count against the entry cap (`count_active_entries` only counts open + active) and surface in three places: result rows at the top of the modal's "your matches" section, panel slots (`you won` / `you lost` / `draw`), and the sidebar `lobby` rule glow. The snapshot's `finished_matches` list is bounded by a 30-day window so a player who never returns can't pin rows forever; migration 108 backfills both seen columns on pre-feature finished rows so old results don't resurface on deploy.

Spectating (added 2026-07-11): the Lobby modal lists other people's active matches under a `live games` section; opening one enters the same full-screen board read-only (`DailyBoardState::spectating`). Every roster game is spectatable; battleship shows only the public hit/miss record on both players' waters, never the fleets (see §4 / `battleship_ui`), and briscola shows both hands as backs (`briscola_ui`). Read-only is enforced three ways: a spectator is never `turn_user_id` (so `play_move`/`board_select_or_move` no-op), `board_resign` early-returns on `spectating`, and `resign` server-side bails "you are not playing in this match". No new data path: `active_matches` was already a global snapshot filtered to "mine" per session.

Non-goals for v1 (deferred by decision, 2026-07-08): wagers/escrow, tournaments, draw offers (chess draws happen only via stalemate/repetition), #lounge announcements, quest wiring. The schema leaves room for all of them (§8).

## 3. Service And Persistence Model [STABLE]

- **No live actor per match.** Every mutation (`post_challenge`, `claim_challenge`, `cancel_challenge`, `play_move`, `resign`) loads the row, validates (chess: `chess_core::rules` over `state.fen`; battleship: `battleship.rs` over the stored fleets/shots; connect4: `connect4.rs` over the drop history), and persists. Nothing to reconcile after a restart. `play_move`'s shared prelude (active status, turn, deadline) runs before the per-game dispatch; a battleship "move" carries the target cell in `to`, a connect4 "move" the column.
- **Snapshot**: one global `watch::Receiver<Arc<DailySnapshot>>` (`open_challenges` + `active_matches` summaries with usernames resolved). Per-session UI filters for "mine". Republished on every mutation; the sweeper loop republishes every 60s as the slow-poll backstop.
- **Events**: `broadcast<DailyEvent>`: `ChallengePosted`, `ChallengeClaimed`, `MovePlayed`, `MatchFinished`, targeted `Error { user_id, message }` for banners (svc error strings lowercase; banners sentence case).
- **Row lifecycle**: `open -> active` (claim) `-> finished | cancelled`. Claim is a guarded UPDATE (`WHERE status='open' AND opponent_id IS NULL`) so two simultaneous claims can't both win; colors are random at claim time and stored in `state.colors`. A `finished` row keeps broadcasting: it rides the snapshot's `finished_matches` list until both players have acked (or the 30-day window lapses), with `mark_result_seen` flipping each player's own seen column exactly once (a repeat ack touches 0 rows and skips the republish).
- **State JSON**, one shape per game, all with a top-level `revision`: `DailyChessState` (version 1: `fen`, `colors`, `move_history` with SAN labels + timestamps, `position_history` for threefold repetition; shared verbatim by chess and chess960, which differ only in the opening `fen`. Every FEN is written in Shredder notation (`rules::fen`) so a shuffled back rank can name its rook files; the old `KQkq` spelling still parses, so in-flight matches were unaffected), `DailyBattleshipState` (version 1: two `sides` of `{user_id, ships, shots}`; ships are contiguous cell lists, shots carry hit + timestamp), and `DailyConnect4State` (version 1: `red`/`yellow` user ids + `drops` column history; everything else derived). `DailyMatch::update_state` and `DailyMatch::finish` share one exact compare-and-swap guard (`STORED_REVISION_EQ_SQL`): the write applies only while the stored `revision` still equals the one the caller loaded, so a superseded write updates 0 rows and the service surfaces "move was superseded". Exact equality (not `stored <= incoming`) matters because a battleship hit keeps `turn_user_id` on the shooter — the turn guard alone can't reject a duplicate same-revision write, so the CAS is what stops last-write-wins there. `update_state` also still guards on the expected mover/turn (a belt-and-suspenders check that also blocks off-turn writes). `resign` reloads and retries on a 0-row (superseded) finish, and stays game-agnostic by deriving the winner from the row and bumping `revision` on the raw JSON.
- **Deadlines are durable by construction**: `turn_deadline_at` is a DB timestamp, never an in-process `sleep_until`. `play_move` rejects a move once `turn_deadline_at <= now()` (and so never resets a dead clock); the sweeper (60s loop) is the forfeit executor for `status='active' AND turn_deadline_at < now()` rows (winner = other player, result `timeout`) and therefore survives restarts for free.
- **Finish payout**: `DailyService::pay_winner` (called from `finish_events`, awaited, not spawned). Gate 1 in Rust: `moves_played < DAILY_WIN_MIN_MOVES` returns `DailyWinPayout::Unplayed` without touching the DB. Gate 2 in the grant: `ChipService::credit_per_event_pair_day_reward_template(game.reward_key(), event_key = match_id, pair_day_key = "<loser id>:<created UTC date>")`, which is `GamePayout::grant_multi` over two `Unique` keys (`event` and `pair_day`) under one advisory lock, all rows or none. Templates stay `claim_policy = per_event`, unchanged since migrations 102-142; no migration in this change. The match key keeps the old idempotency (a sweeper retry never double-pays); the pair-day key is the cap. `credited = false` on a first finish is therefore the cap (`PairDayCapped`), because the match key cannot collide there. A credit error is `Failed`: logged, the match still finishes. Every outcome is one `late_ssh_daily_win_payouts_total{outcome}` count (`metrics::record_daily_win_payout`) and is written to `daily_matches.win_payout` (`DailyMatch::set_win_payout`, a second UPDATE after the finish, by design: the payout is decided once the finish is durable, and a failed credit must never un-finish a match; a failed write of the column loses only the result-row phrase and is logged). The column is CHECKed to the four `DailyWinPayout::db_str` spellings, NULL for draws and pre-gate rows.
- Results: `checkmate`, `draw`, `fleet_sunk`, `four_in_a_row`, `most_discs` (reversi), `no_moves` (checkers win by block/capture), `borne_off` (backgammon), `resign`, `timeout`, `''` while running. Battleship and backgammon cannot really draw (backgammon's stall cap is a defensive `draw`); connect four, reversi, and checkers can draw (winner `None`, no payout, like chess draws).

## 4. UI Surfaces [VOLATILE]

### Sidebar panel (`panel.rs`)
- Fixed 6 rows: four match slots, one status line (`N open · entries/cap`), key hints (`` ctrl+q · ` toggle ``). Slots render dashes when empty; the panel never changes height between states (stable-chrome rule).
- Slot order is actionable > news > waiting: your-turn rows first (nearest deadline within), then unseen results (`you won` / `you lost` / `draw`, glowing in success/error/amber), then waiting rows. Since the cap (10) now exceeds the four slots, the panel is a deliberate **top-4 view**: the actionable/your-turn matches always win the slots and the tail (typically waiting rows, plus any overflow from unseen results) lives in the modal. Result rows still self-clear the moment the player looks (see §6).
- The panel has no title row: the sidebar's labeled separator rule (`── lobby ────`, built in `app/common/sidebar.rs::draw_panel_rule`) is the title. Every sidebar panel's rule is labeled this way; the lobby's label is the only one with an active state.
- Attention is split across two signals: the rule label glows while it's your turn in any match OR an unseen result is waiting (the sidebar computes this from `DailyState::my_matches`/`my_turn`/`my_finished`); the status line's open count glows while there are open challenges unseen since the modal was last opened (the liquidity signal; owned by `LobbyState`, passed into the panel as a bool). Own challenges never glow. `LobbyState::seen_open_ids` is seeded at session start so pre-existing challenges don't glow on login (result rows deliberately DO survive login — that persistence is their whole point).

### Lobby modal (`modal_*`)
- Lives in `../modal_input.rs` / `../modal_ui.rs` (it fronts both game domains). Opened by reserved global `Ctrl+G` only (works anywhere, including while composing; pressed again it closes the modal). The old bare `g` binding is removed. Opening calls `LobbyState::mark_seen`.
- Near-fullscreen: sized from the terminal minus a margin (8 cols / 4 rows), capped at 100x40 so lines stay readable on large terminals. The daily surface is a primary destination, not a peek.
- One scrollable list, `j`/`k`: your matches (unseen result rows first — `you won · checkmate` / `you lost · timeout` with an `enter view · x dismiss` hint — then active matches; Enter opens the board), then every open challenge (Enter claims with a confirm second-press; `x` cancels your own), then a `live games` section of other people's spectatable active matches (Enter opens the board read-only). The live-games header is hidden when there are none. Rows show the game and its chip prize (spectate rows show `challenger v opponent` + whose move it is instead). Result phrasing comes from `state.rs::result_phrase`.
- `c` / `C` open the challenge picker: a small centered overlay on the modal with one row per roster game and its prize (`j`/`k` + Enter), so the roster scales without fighting the status line for width. Directed drafts (`C`) add a username step after the game is picked; `Esc` steps back (username → picker → closed), and confirm consumes its own first Esc.

### Board screen (`board_*`, `battleship_ui.rs`, `connect4_ui.rs`)
- `Screen::DailyMatch`, outside the Tab cycle, entered only from the modal; `q`/`Esc` restores the return screen and reopens the modal (one keypress per hop across matches). Renders whichever game the match is; the screen title is "Daily Match".
- Leaving the board of a finished match you played acks its result (`DailyState::ack_finished_result`, fired from `close_board` AND from `open_board_inner` when hopping straight to another match). Conservative by design: if the final reload never landed (detail missing or still showing active), no ack — the player never saw the result, so the row stays.
- Spectator mode (`DailyBoardState::spectating`, set in `open_board` when you're neither player): read-only. No cursor (every renderer gates the cursor on `my_turn`, which a spectator never is), the key-hint row shows `watching` instead of move/resign hints, and `board_resign` is a no-op. Live reload still fires (the reload keys purely on `board.match_id`), so a watched game updates move-by-move and shows the result overlay on finish. Chess renders in White orientation; connect four defaults a spectator to red's perspective. Battleship swaps its "their waters / your fleet" pair for two ships-hidden `spectate_waters_lines` grids (one per player, titled by name) that show only hits/misses — the fleets are never drawn, even on finish.
- Connect four layout: one centred grid (header letters, a `▼` indicator over the cursor column, ghost `◌` at the landing cell, drop count under the board), player bars showing disc colors, and a drop-history rail when wide enough. `arrows/wasd` slide the column cursor (the cursor IS a column index), `Space`/`Enter` drops (optimistic, `drop_in_flight` blocks a double drop until the reload), mouse drops via `target_geometry` (click maps to a column). The winning four render as solid tiles under the result overlay.
- Battleship layout: "their waters" target grid (left, cursor + fired shots; unfound enemy ships revealed as `░░` when the match ends) beside "your fleet" (right, ships + incoming fire), per-grid sunk/afloat summaries, player bars with afloat counts, and a salvo-history rail when wide enough. `arrows/wasd` aim, `Space`/`Enter` fires (optimistic, `shot_in_flight` blocks a double salvo until the reload), `r` resign, mouse fires via the render-recorded `target_geometry`.
- Backgammon layout: the classic two halves (point numbers in the viewer's own counting, home board bottom-right), checker stacks growing toward the middle, bar and off tray as first-class cursor columns, dice + hops-to-play in the middle gap. Lift/land with Space/Enter or clicks; the pending turn previews on the board and sends the moment it matches a complete legal turn.
- Vertical layout: the status line and the two player bars ride with the board as one centred group, so the colour/name labels always hug the board edges. The key-hint row is the exception and pins to the last row of the content column, with a `Min(0)` slack row absorbing the gap. Board sizing still reserves all four chrome rows (`CHROME_ROWS`), so pinning the hints does not change the tier the board picks.
- Loads the full row on open and on every `MovePlayed`/`ChallengeClaimed`/`MatchFinished` for the open match id (reload coalescing via `reload_pending`). Usernames are captured at open so names survive the match leaving the active snapshot on finish.
- Match chat pane: players (never spectators) with a `chat_room_id` get the embedded chat + voice strip below the board (same `EmbeddedRoomChatView`/`draw_embedded_room_chat` as the active room; the strip renders when the voice channel is enabled, `Ctrl+V`/`Ctrl+T` work unchanged). The slab takes a third of the height clamped to 9–13 rows and drops entirely under 27 rows; the board sizes itself in what remains. Keys mirror the active-room split: `i` composes, `j`/`k` select messages, message-action keys apply while a message is selected (`r` is reply then, resign otherwise), arrows belong to the board only while it's your move, Esc peels selection → board close. `` ` `` continues the lobby cycle from here.
- Move flow mirrors table chess: cursor + Space/Enter or mouse click, promotion defaults to queen, `r` resign (press twice), `p` toggles piece graphics. Castling takes either gesture, king first: onto your own rook (the cozy-chess encoding) or two squares toward it (lichess/chess.com); both land the same move and record identically, see `app/games/CONTEXT.md`. In chess960 the two-square push exists only when the king started on e1/e8, so the rook gesture is the one that always works; the board's info rail carries that as the game's tagline. The rail is 22 columns wide and wraps, so its move-list budget counts the rows the header renders into, not its lines: budgeting by line lets a tagline wider than the rail push the newest move pair off the bottom. The optimistic move applies locally and reconciles on the next reload; legal moves are cleared until then so the cursor can't pick up opponent pieces.
- Piece-graphics image ids seed from `match_id` (the `placement_seed` param of `chess_core::board_ui`).

## 5. Notifications [STABLE]

- **Your-turn desktop notify**: `DailyState` holds a cloned `notify::Notifier` and pushes `Notification::daily_your_turn(opponent)` (`Kind::GameEvents`) on the became-my-turn edge while connected. Edge detection: `turn_notified_match_ids` is seeded from the login snapshot (connecting never notifies; the panel's glow + your-turn rows are the on-login nudge) and pruned when the turn passes away, so a turn coming back is a fresh edge.

Offline players are covered by the durable result rows (§4), not by banners. There is deliberately no finish desktop notification in v1; the lingering row is the nudge.
- **#lounge result line**: added — a finished match posts one system line to #lounge via the standard activity path (`ActivityKind::DailyResult` → `filter::lounge_includes` → `activity/lounge.rs`), NOT a bespoke `DailyEvent`/ghost-bot path. See §1. Only finishes publish; posting and claiming stay silent, and there is still no quest wiring.

## 6. Critical Invariants [STABLE]

- Daily matches never touch the house-table runtimes; house tables never reach into `daily_matches`. The only shared code is `chess_core` (and `ChipService`). `DailyService` and `HouseTableRegistry` stay separate services — no unifying trait, no `GameSurface` abstraction.
- The game roster is `games.rs::DailyGame` and nothing else: no game-kind string comparisons outside `DailyGame::from_kind`/`kind()`. Rows whose `game_kind` this build doesn't know are hidden from the snapshot (and skipped for payout with an error log), never guessed at.
- `DailyGame::win_payout` is display-only; the seeded reward template pays. Keep them equal.
- The lobby is not a faucet. Every win credit goes through `pay_winner` and its two gates; no finish path credits chips on its own. Known and accepted: the pair-day cap bounds one pair at one win per game per posting day, not one account. A colluding pair's ceiling is one paid win per roster game per direction per day (about 3,300 chips each way, and they have to play all eight games), and five alt accounts are ten pairings. If Top Chips ever looks wrong, group `chip_ledger` daily-win rows by `(winner, opponent)` over 30 days; a per-account daily quota would need a counting arm on `GamePayoutKey`, deliberately not built.
- **Known, not fixed: the finish path nests pool connections.** Every play path, `resign`, and `sweep_expired` hold their pooled `client` across the awaited `finish_events`, which takes a second connection for the grant (`pay_winner`) and a third for `set_win_payout`. The pool is 16 with a 5s wait (`late-core/src/db.rs`), so enough simultaneous decisive finishes could starve it; the grant would then time out, fold into `DailyWinPayout::Failed`, and the win stays unpaid with `win_payout = 'failed'` on the row (recoverable by hand from that column, never silently). Left as is on 2026-08-27 because correspondence finishes are a few a day. Fix when the lobby gets busy or when the wager rewrites these paths: pass the held `client` into `pay_winner` / `record_win_payout`, or drop it before the await and re-acquire for `publish`.
- Claim stays a guarded UPDATE; never split it into read-then-write without the status/opponent guard.
- Deadlines stay DB timestamps. Do not introduce in-process timers for correspondence deadlines; a `sleep_until` clock does not survive restarts and this domain must.
- The entry cap (`DAILY_MAX_ACTIVE_ENTRIES`, 10) counts open challenges posted plus active matches played, enforced server-side on post AND claim. It exceeds the panel's `MATCH_SLOTS` (4) by design: the panel is a top-4 view (your-turn rows first, nearest deadline within), so the actionable matches always hold the slots while waiting rows and any overflow live in the Lobby modal, which shows the full set. Unseen finished results never count against the cap; in the slots they displace waiting rows, never your-turn rows, and clear on first look.
- Result acknowledgment is per-player and only ever touches the acker's own seen column; nothing may ack on another player's behalf, and merely opening the modal must not ack (only leaving the board or an explicit `x`).
- `state.revision` only increases; superseded writes must fail loudly ("move was superseded, reload the match"), not last-write-win.
- Panel height is constant (6 rows); empty slots render dashes. Never collapse or grow the panel between states.
- Match chat is players-only: memberships are written once, in the claim transaction; `join_game_room` rejects non-members for private game rooms; spectators get no chat pane and no read access (membership is the auth for tails/sends). Nothing may add a third member.
- Chat rides the match lifecycle: created at claim (never at post), reaped 30 days after finish/cancel by the sweeper. Every surface must tolerate `chat_room_id = NULL` (pre-109 matches, post-reap rows).
- The backtick cycle is Home chat + your-turn boards + seated house tables + unfinished Arcade dailies (`app/workspace/arcade.rs::ArcadeStop`: today's daily boards with player moves, not solved — never real-time games or personal boards). Do not re-add rooms stops; new workspace kinds go through the `GameWorkspace` enum.
- The ONLY activity daily games publish is the finish result line (`ActivityKind::DailyResult`, §1/§5): one per match, on finish only, never on post/claim. No other `ActivityEvent`, no direct chat writes, no quest signals. New games inherit this automatically — `finish_events` is the single choke point and `DailyGame::display_name()` is a required exhaustive method.
