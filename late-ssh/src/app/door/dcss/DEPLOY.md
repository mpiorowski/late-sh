# DCSS door: build, config and deploy

How the `late-dcss` host is built, configured and shipped. The door's shape,
transport and invariants are in `CONTEXT.md`; the generic door module and
release flow are in `infra/` and the root `CONTEXT.md`.

## Client (env → `Config` → `SessionConfig` → `App`)
- Client enabled/host/port are profile literals in `late-ssh/src/config.rs` (dev `service-dcss`, prod `late-dcss-sv`, port 2325); `LATE_DCSS_SECRET` is the only env the client reads (must equal the host's).

## Host (`late-dcss` env)
- `LATE_DCSS_SECRET` (required), `LATE_DCSS_BIN` (default `/usr/games/crawl`), `LATE_DCSS_DATA_DIR` (default `/var/lib/late-dcss`; the child `HOME` = the PVC in prod), `LATE_DCSS_LISTEN_ADDR`, `LATE_DCSS_PORT` (default `2325`), `LATE_DCSS_PUBLISH_PORT` (default `2329`; the read-only crawl-file listener, same bind address), `LATE_DCSS_IDLE_TIMEOUT`.

## Binary sourcing — built from verified upstream source, DCSS 0.34.1
- Compiled in the `dcss-build` stage (`docker/doors/dcss.Dockerfile`, published as the ghcr `door-dcss` image the root Dockerfile pins) (NOT the distro `crawl` package, which lags: bookworm ships 0.29). The stage downloads the pinned release tarball from GitHub, verifies SHA-256 (`sha256sum -c`, fail-closed), then runs the release's own documented install (`make install prefix=/opt/dcss NOWIZARD=y`, console build — tiles needs an explicit `TILES=y` we never pass; `NOWIZARD=y` compiles out wizard/cheat mode for untrusted players, asserted fail-closed via the binary's `-version` CFLAGS line). Version/URL/checksum are `ARG`s (`DCSS_*`).
- The build passes `EXTERNAL_DEFINES="-DDGL_MILESTONES -DTIME_FN=gmtime -DDGL_EXTENDED_LOGFILES"` — three dgamelaunch-server behaviors the plain build leaves off (normally implied by `DGAMELAUNCH`, which we deliberately do NOT define wholesale). `DGL_MILESTONES` makes `mark_milestone` write the milestones file at all (verified against the pinned source: without it the file simply never exists), `TIME_FN=gmtime` puts the xlog timestamps in UTC (localtime otherwise), and `DGL_EXTENDED_LOGFILES` adds the preformatted `tmsg` death one-liner the feed events use. Each is asserted fail-closed via the `-version` CFLAGS grep, same as `NOWIZARD`. Bumping the recipe bumps the `door-dcss` image tag in the root Dockerfile and `dcss.yml`.
- The install bakes `DATADIR=/opt/dcss/data` into the binary and leaves `SAVEDIR` at the default `~/.crawl`, so the data tree is a read-only image layer while all writable state follows the child's `HOME`.
- No source is patched (contrast nethack's unixconf.h edits). crawl has no in-game shell escape to compile out; the one hardening knob is `NOWIZARD=y` above.

## Images / infra / CI
- `runtime-dcss` stage: crawl runtime libs (`libncursesw6`, `liblua5.4-0`, `libsqlite3-0`) + `ncurses-term`, the `/opt/dcss` tree, `/usr/games/crawl` symlink, `/var/lib/late-dcss` chowned to `late`. `base` gets the same tree for `dev-dcss` (compose `service-dcss`).
- `infra/doors.tf` (`dcss` entry, stamped out by the `infra/door` module): the RWO `dcss-save` PVC (2Gi, `prevent_destroy`) and the `late-dcss` Deployment (replicas **1**, kill-before-create, `terminationGracePeriodSeconds=30` > `SHUTDOWN_GRACE`, `dcss-save-seed` initContainer that only chowns the mount — crawl mkdirs its own `~/.crawl`) + the `late-dcss-sv` ClusterIP Service on 2325 (game) and 2329 (crawl files) + the `late-dcss-crawl-ingress` `Prefix` rule (a plain resource in doors.tf, outside the module) putting the publisher on `late.sh/crawl`. That ingress carries no tls block and no cert-manager annotations on purpose: ingress-nginx merges rules per host, so it reuses `service-web-ingress`'s certificate for the apex domain instead of racing it for a second one. The `dcss-identity-secret` (from the door module) is injected into both service-ssh and late-dcss.
- CI: `-dcss` releases route through `release.yml` to the generic `deploy_service.yml`: `ci` + `build`, then `kubectl set image deployment/late-dcss '*=<image>'` (covers the `dcss-save-seed` init container and the main container) and a rollout wait. No terraform runs on ordinary releases, so nothing else in the cluster is touched; when the `late-dcss` deployment is missing the run auto-bootstraps (a terraform apply `-target=module.door["dcss"]`; the `late_dcss_crawl` ingress lives outside the module in `infra/doors.tf` and ships through `deploy_infra.yml`). Other manifest changes go through `deploy_infra.yml` too — including the publish port and its ingress, so shipping the publisher to a live cluster is an infra deploy, not a `-dcss` release; terraform never reads or rewrites live image tags (deployments carry `ignore_changes` on images), so an ordinary release never rebuilds or restarts the door. Same rule as every other door. `doors.yml` (PR/weekly build-validate of `docker/doors/dcss.Dockerfile` via `docker/doors/smoke/dcss.sh`, publishes the pinned `door-dcss` image on main pushes at the tag pinned in the root Dockerfile, manual verify_deployed). ## Why `macro_dir`/`save_dir` are compiled out

Root cause, confirmed against the pinned crawl 0.34.1 source: our Dockerfile builds `make install prefix=/opt/dcss`, and crawl's own `Makefile` has a rule (`ifneq ($(patsubst /opt%,%,$(prefix)),$(prefix))`) that force-sets `SAVEDIR := ~/.crawl` for any `/opt` prefix, which bakes `-DSAVE_DIR_PATH` into the binary. `initfile.cc` then registers `{"save_dir", "macro_dir"}` as `DisabledGameOption` whenever `SAVE_DIR_PATH` is defined, and `DisabledGameOption::loadFromParseState` (`game-options.cc`) returns an `"Option 'X' is disabled in this build."` error for **any** source, rc file or `-extra-opt-last` alike. A pushed rc cannot override `-macro` with its own `macro_dir =` line: because `macro_dir` is disabled outright on this build, that line is rejected by the same `DisabledGameOption` path (a non-fatal parse error there, unlike the fatal command-line form), so there is no cross-player hole to guard. A defensive `-extra-opt-last macro_dir=<dir>` re-force in `host.rs::crawl_args` breaks every launch (`Options error: Option 'macro_dir' is disabled in this build.`). `-macro <dir>` alone (via `SysEnv.macro_dir`, consumed directly outside the option system) remains the correct and only mechanism. If a future crawl version or build recipe changes (e.g. `prefix` stops matching `/opt%`, or `SAVEDIR` gets explicitly overridden), re-verify against the actual Makefile before touching `crawl_args` again, never from generic upstream docs.
