# Brogue door: build, config and deploy

How the `late-brogue` host is built, configured and shipped. The door's shape,
transport and invariants are in `CONTEXT.md`; the generic door module and
release flow are in `infra/` and the root `CONTEXT.md`.

## Client (env → `Config` → `SessionConfig` → `App`)
- Client enabled/host/port are profile literals in `late-ssh/src/config.rs` (dev `service-brogue`, prod `late-brogue-sv`, port 2327); `LATE_BROGUE_SECRET` is the only env the client reads (must equal the host's).

## Host (`late-brogue` env)
- `LATE_BROGUE_SECRET` (required), `LATE_BROGUE_BIN` (default `/usr/games/brogue`), `LATE_BROGUE_DATA_DIR` (default `/var/lib/late-brogue`; the playground root = the PVC in prod), `LATE_BROGUE_LISTEN_ADDR`, `LATE_BROGUE_PORT` (default `2327`), `LATE_BROGUE_IDLE_TIMEOUT`.

## Binary sourcing: built from verified upstream source, Brogue CE 1.15.1
- Compiled in the `brogue-build` stage (`docker/doors/brogue.Dockerfile`, published as the ghcr `door-brogue` image the root Dockerfile pins) from the pinned GitHub tag tarball, SHA-256 verified fail-closed (`BROGUE_*` ARGs). Build: `make bin/brogue TERMINAL=YES GRAPHICS=NO RELEASE=YES` (curses-only, no SDL; RELEASE drops the `-dev` version suffix that brogue bakes into save names). Two source patches, `scripts/brogue_hangup_save.patch` and `scripts/brogue_victory_log.patch` (`CONTEXT.md` §1), each applied with its own fail-closed grep (`handleHangup` present; `GAME_MODE_NORMAL` gone); the stage also runs `scripts/brogue_verify_isolation.sh` (the `CONTEXT.md` §4 save-isolation assertions, ~0.2s) and asserts `--version` prints exactly `Brogue version: CE <version>`. Every grep and the script gate the `make`, so a source that fails any of them never produces a binary.
- The terminal build reads no data files (DATADIR only matters for graphics assets), so there is no read-only data tree: `/opt/brogue/brogue` is the whole install, symlinked to `/usr/games/brogue`.
- **A local copy of that exact source lives at `upstream-brogue/` in the repo root** (gitignored, alongside `upstream-lotgd/` and `upstream-adarkroom/`; the re-fetch command with the SHA-256 check is in `.gitignore`). It is pinned to the same tag and hash as the Dockerfile, so it is the authority for questions the door's behavior inherits from upstream, the `CONTEXT.md` §4 save-isolation invariant especially. Read-only: we link nothing from it, and the only changes we make to upstream are `scripts/brogue_hangup_save.patch` and `scripts/brogue_victory_log.patch`. **Re-pin it in the same commit as any CE bump**, or it silently stops describing the running binary.

## Images / infra / CI
- `runtime-brogue` stage: `libncurses6` (the build links plain `-lncurses`, not ncursesw) + `ncurses-term`, `/opt/brogue`, the `/usr/games/brogue` symlink, `/var/lib/late-brogue` chowned to `late`. `base` gets the same binary for `dev-brogue` (compose `service-brogue`).
- `infra/doors.tf` (`brogue` entry, stamped out by the `infra/door` module): the RWO `brogue-save` PVC (2Gi, `prevent_destroy`) and the `late-brogue` Deployment (replicas **1**, kill-before-create, `terminationGracePeriodSeconds=30` > `SHUTDOWN_GRACE`, `brogue-save-seed` initContainer that only chowns the mount; the host mkdirs the player dirs itself) + the `late-brogue-sv` ClusterIP Service on 2327. The `brogue-identity-secret` (from the door module) is injected into both service-ssh and late-brogue.
- CI: `-brogue` releases route through `release.yml` to the generic `deploy_service.yml`: `ci` + `build`, then `kubectl set image deployment/late-brogue '*=<image>'` (covers the `brogue-save-seed` init container and the main container) and a rollout wait. No terraform runs on ordinary releases, so nothing else in the cluster is touched; when the `late-brogue` deployment is missing the run auto-bootstraps (a terraform apply `-target=module.door["brogue"]`). Other manifest changes go through `deploy_infra.yml`; terraform never reads or rewrites live image tags (deployments carry `ignore_changes` on images), so an ordinary release never rebuilds or restarts the door. Same rule as every other door. `doors.yml` (PR/weekly build-validate of `docker/doors/brogue.Dockerfile` via `docker/doors/smoke/brogue.sh`, publishes the pinned `door-brogue` image on main pushes at the tag pinned in the root Dockerfile, manual verify_deployed).
