# Cyberspace: cIRC, their chat as a rail section

How linked cyberspace chat rooms and C-Mail conversations live in the Home
rail: the section, the `/cs` commands, the room picker, the conversation view,
fetching only where the user is, the unread dot, and the dynamic slot. Part
of the cyberspace slice (`CONTEXT.md`: the API terms, linking, the feed pane,
invariants, tests).

Their API docs are public at https://api.cyberspace.online/docs (markdown at `/docs.md`; their WAF 403s non-browser user agents, so fetch with a browser UA).

**Shape.** Linking cyberspace gives the rail its own collapsible `cyberspace` section (`RoomSection::Cyberspace`, shortcut `y`) holding **`feeds`** (`RoomSlot::Cyberspace`, the feed/thread pane, kept out of Core because the chat rooms beside it are cyberspace too), **`notifications`** (`RoomSlot::CyberspaceNotifications`, the same pane with its root view on the notifications list), one row per added chat room, and one per pinned C-Mail conversation (`RoomSlot::CyberspaceMail`). The section renders only while `cyberspace_linked`, so an unlinked user's rail is untouched.

**Our own `/cs` commands work from a room composer, and never reach their API.** `handle_room_composer_input` parses the draft with `parse_cyberspace_command` before submitting: `/cs chat` and `/cs mail` are answered locally (their pickers open *over* the room), `/cs mail @user` starts the conversation and deliberately walks the user into it (below), every other `/cs …` is refused with a banner naming the three, and anything the parser does not recognise is sent exactly as typed, because `/me`, `/dice`, `/mute` and friends are theirs and expand server-side. Commands that would move the user (`/cs`, `/cs post`, `/cs link`, `/cs unlink`) stay with the main chat composer, where moving them is not a surprise. The feed pane advertises no commands at all: it has no composer to type them into.

**Leaving a room goes back to the row it was entered from** (`ChatState::cyberspace_return_row`, a `CyberspaceRow` noted before the room takes the selection). Landing on `feeds` after arriving from the notifications row, which is what a mention jump does, reads as being thrown somewhere else.

**A chat mention is the other way in.** Enter on a `chat_mention` row in the notifications view pins the room it names (if it is not pinned already) and walks into it, because their payload names a room and nothing finer (`CONTEXT.md` §6b). Pinning first is not optional: the rail entry is how a room is entered, and the chat tick leaves any open room the pinned list cannot name.

**Rooms are added through a picker, and adding one is what creates its rail entry.** There is no join/leave over there: `GET /v1/circ` returns the rooms this account may read and that roster is what it is, so our list is a bookmark. `/cs chat` (alias `/cs rooms`) opens `Modal::Rooms`, a checklist of their roster with online counts; Enter adds the highlighted room to the section or takes it off. Command only, deliberately: a single letter would have to be pressed on the feeds pane specifically, which is the one place a user looking for rooms is least likely to be standing, and the pane's letters are otherwise all reading actions. The picker deliberately does **not** open rooms: a room is entered by selecting its rail entry, like every other room in the rail.

**The conversation is pre-wrapped, same contract as the thread view.** `room_lines(messages, width)` returns one `Line` per rendered row, wrapping each message's text under a hanging indent so the author is named once. Handing `Wrap` to the paragraph instead makes the scroll window lie: it counts rows, and a wrapped message occupies more rows than the one it is counted as, which pushes the newest messages off the bottom. The renderer writes the row ceiling into `OpenRoom::max_scroll` (a `Cell`, like `thread_max_scroll`) and `room_scroll` clamps against it, because only the renderer knows the width the text wrapped to.

**A room writes through the chat composer slot, not its own box.** `draw_room` renders only the header and the conversation; the composer `TextArea` lives on `OpenRoom` but is drawn by `chat::ui` into the footer block it shares with the pane's hint line (titled with the room's name while one is open). A second bordered input inside the pane would stack two boxes over each other and make a room look unlike every other room. It is single-line for the same reason: that slot is one row, and their API takes one message per send. **Entering a room lands in reading mode, not in the composer** (`OpenRoom::composing`): `i` or Enter focuses it, Esc drops back out of it, and a second Esc leaves the room. `app::input` routes every keystroke into the composer only while it holds focus, so a room being read keeps `j/k`/`g`, the rail shortcuts, and every other global letter, exactly like every other room in the rail. Focusing on entry would make all of them text. Sending follows the profile's `keep_composer_focused` tweak, the same as the main chat composer.

**Writing to someone new is `/cs mail @user`** (alias `/cs dm @user`), which is their documented way to start a conversation: `POST /v1/cmail { recipientUsername }` is idempotent, returning the existing conversation (`200`) or creating one (`201`). `CmailStarted` pins the row, banners it, and records the id in `started_cmail`; the chat tick takes it, selects the row and pulls the user to Home, because naming someone is asking to write to them, not asking for a new rail row to go find. Their caps: 5/min, 30/hour, 50/day on starting conversations, 15/min, 150/hour, 300/day on messages.

**Persistence is ours and tiny.** `cyberspace_accounts.circ_rooms` (migration 137) is the ordered pinned slugs, replaced wholesale on every change, and `circ_room_reads` (migration 139) is one jsonb map beside it: slug → the newest message timestamp seen while the user was inside, on their clock, pruned to the pinned list whenever that list is rewritten. Nothing else lands in our DB: names and online counts come from their roster on demand, and their own read state stays on their side (`POST /v1/circ/:roomId/read`, written when a room opens; it is write-only, which is why the dot cursor is ours). `LinkStatus` carries the list and the cursors at session init, beside the feed cursor.

**Fetch only where the user is.** `CircRoomSession` (svc.rs) is the whole contract: holding one is what makes a room fetch anything, and `Drop` aborts its three tasks and announces the user out of the room. Entering loads history (`GET /v1/circ/:roomId?limit=50`), opens one SSE stream on their realtime database (`<rtdbUrl>/chat_messages/<roomId>.json?auth=<idToken>`, always `orderBy="timestamp"` and `limitToLast` ≤ 100; frames are reassembled from raw bytes by `CircStreamBuffer` and decoded once per complete frame, so a chunk boundary inside a multi-byte character cannot mangle text), and heartbeats presence at the `heartbeatMs` their own response names, never a hard-coded one, floored at `CIRC_PRESENCE_MIN_HEARTBEAT_MS` when parsed so a misbehaving response cannot dictate a hot loop. Every path out of a room drops the session: `ChatState::clear_synthetic_selection` calls `leave_room` (selecting anything else in the rail is leaving), `App::set_screen` calls `ChatState::close_cyberspace_room` (leaving Home entirely is leaving too, and Esc is not the only way off the screen), and the chat tick leaves a room the pinned list can no longer name. A background stream would be a fetch with no human behind it, which is the whole of `CONTEXT.md` §3. The stream reopens when the ~60 min id token expires and gives up after `CIRC_STREAM_MAX_FAILURES`, publishing `CircStreamEnded` rather than reconnecting in a loop (their docs ask for exactly that). `rtdbUrl` rides the login/refresh response into the token cache.

**The `feeds` badge reads as a floor once the probe page fills.** Unread entries are counted out of a page of `UNREAD_PROBE_LIMIT` (10), so ten means "at least ten"; `room_slot_badge` renders `9+` in that case rather than a total it cannot stand behind (rooms keep their own `99+` SQL cap).

**A chat room's unread state is a dot, never a count.** Their roster reports `last_message_at` per room but never reads back read state, and a number (even a saturated one) would take a per-room history fetch every poll: authenticated calls with nobody behind them, growing with every pin. The dot costs exactly one roster call riding the existing 10-minute badge refresh, fetched only while rooms are pinned, and compares each room's `last_message_at` against our own read cursor (`circ_room_reads`, above; same clock on both sides, so skew never enters into it). **Entering a room always clears its dot**, before a single message has loaded: `stamp_open_room_read` runs on entering, on history landing, on a roster arriving while the room is open, and on leaving, and it takes the roster's own `last_message_at` as a floor under the newest message on screen. Stamping from the messages alone is not enough: a room whose history call failed, came back empty, or carried nothing stampable would keep its dot forever, and only writing a message (which arrives back through the stream) could clear it. Reading the roster's own value also keeps the comparison like for like, so the two halves of the dot can never drift apart. The cursor only ever moves forward and is persisted fire-and-forget. The open room never shows a dot, because a room is read by being in it, the way an IRC channel is; a room never visited shows nothing rather than claiming a backlog the user was never behind on. Mentions still ride the existing notification badge.

**Navigation lands in five mirrors**, and `CONTEXT.md` invariant 3 covers all of them: `visual_order_for_rooms`, `build_cozy_room_rail_rows` and `build_room_list_rows` (the two rail builders, whose `hit_slots` are the click mirror), `RoomSection` (label/shortcut/`from_label`), and the `Ctrl+/` jump modal (`room_search_modal/state.rs`). `Space` room-jump comes free once the slots are in `visual_order`.

**The slot is dynamic, unlike every other synthetic entry.** `SelectedRoomSlotState` is `Copy` and a slug is not, so `RoomSlot::CyberspaceRoom(usize)` carries the index into the pinned list and `ChatState::cyberspace_room_selected` is the same index. The pinned list can change under that index (`toggle_selected_room` in this session, a `CircPinned` broadcast from another session of the same account, an unlink), so the chat tick re-derives it from the open room's slug every frame: the cursor follows the room through a reorder, and a room the rail can no longer name is left, landing the user back on the pane. The bool-per-entry selection clears through `clear_synthetic_selection`, so a new entry cannot half-clear the others.

**Rendering, from their docs** (`CircMessage::display_text`, tested in `api_test.rs`): `content` can be empty (an image, GIF or song is the whole message, and a website post sometimes repeats the attachment URL as `content`, which prints the link twice if taken literally); a delete arrives as a `patch` that rewrites a message already on screen, so it is applied in place and never appended; `style: "art"` means `content` is base64 ASCII art; `isAction` renders `* username content`. `/me` and friends expand server-side, so they are sent as plain text. Messages cap at 2,048 chars; sending is 15/min, 150/hour, 300/day.

**Not built:** guild threads, deleting your own messages (`DELETE /v1/circ/:roomId/messages/:id`, we only render the tombstones), scrollback paging (`before` is plumbed through `read_circ_room` but nothing calls it yet), the live presence stream (`chat_presence/<roomId>`), and any generic "integrations" abstraction. There is one integration; the section is named for it and its code stays in this slice.
